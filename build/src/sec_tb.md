# 출처: 드라이브 교재_보안 (2026-11-15, 학원 해설 보충 포함)

# A. 제로트러스트

## 쉽게 먼저 (ZT)
옛날 보안은 **성벽**이에요. 성문(방화벽·VPN)에서 한 번만 검사하고, 안에 들어오면 다 믿어요. 제로트러스트는 **방마다 카드를 찍는 건물**이에요. 안이든 밖이든 아무도 믿지 않고, 요청할 때마다 "누구냐, 무슨 기기냐, 지금 상황이 평소랑 같냐"를 다시 따져요.

한 줄 이야기: 성벽 하나 믿다가 → 안에서 뚫리고 재택·클라우드로 성벽도 흐려지니까 → 요청마다 다시 검사하는 게 제로트러스트.

기출: 131회 2교시 · 134컴 1교시 · 135회 4교시 · 135컴 3교시(정의·핵심 원칙 / 구성요소 / 성숙도 4단계 / 도입 절차) · 140컴 4교시(가이드라인 2.0 의의 / 아키텍처) · 136회 4교시(공급망)

## 정의 (ZT)
네트워크가 이미 침해됐다고 가정하고, 모든 접근 요청을 신원·기기·상황 기반으로 매번 검증해 최소 권한만 허용하는 보안 모델 (Never Trust, Always Verify)

## ⚠️ 학원 핵심 원칙 = 구현 3원칙 (135컴 가 · 131)
- **인증 체계 강화**: 모든 접근 비신뢰, 중앙 집중 정책·접근제어, 사용자·기기 인증, 지속적 검증
- **마이크로 세그멘테이션**: 자원을 잘게 나눠 배치, 최소 권한, 단위별 접근과 보호
- **소프트웨어 정의 경계(SDP)**: 논리 경계 생성, 세션 단위 접근, 통신 보호
- (마이크로소프트식 3원칙: 명시적 검증 · 최소 권한 · 침해 가정 — 같이 알되 소제목은 학원 것)

| 신뢰 기준 | 위치 | 신원·기기·상황 |
| 검증 시점 | 경계 진입 시 1회 | 요청마다 지속 검증 |
| 보호 단위 | 네트워크 경계 | 개별 자원 (마이크로 세그멘테이션) |

# B. N2SF

## 쉽게 먼저 (N2SF)
공공기관은 업무망과 인터넷망을 **물리적으로 완전히 끊어**(망분리, 2006~) 생성형 AI·클라우드를 못 써요. N2SF는 "모든 걸 끊지 말고 **정보 중요도에 따라** 방을 나누자" — 금고방(C)은 꽁꽁, 사무실(S)은 조건부, 손님방(O)은 외부와 자유롭게. 핵심은 **높은 등급 → 낮은 등급으로 넘어가는 지점**을 막는 것.

기출: 137회 3교시(가. 개념 / 나. 적용 절차 / 다. 고려사항) · 140컴 1교시

## 정의 (N2SF)
- 교재: 국가·공공기관 업무정보와 정보시스템을 기밀(C)·민감(S)·공개(O) 등급으로 분류하고 등급별 보안통제를 차등 적용하는 국가 망 보안 프레임워크
- ⚠️ 학원(137 가): 주요 기반시설과 국가·공공기관의 핵심 기능과 업무 연속성을 보호하기 위해 위협식별, 위험 파악, 보호대책 수립·적용을 포함한 보안 원칙과 절차를 제공하는 보안 프레임워크
- 흐름: 2024.9 국정원 MLS 공개 → N2SF → 2025.1 가이드라인 초안 → 2025.9 가이드라인 1.0

## C/S/O 등급
| 등급 | 대상 | 망 처리 |
|---|---|---|
| C 기밀 | 비밀·국가안보·생명 | 물리적 망분리 유지 가능 |
| S 민감 | 기관 고유 업무, 비공개 개인정보 | 논리적 분리(SDP·가상화), 외부 이동 통제 |
| O 공개 | 공개 가능 정보 | 외부 클라우드·생성형 AI 연계 가능 |

정보 이동: 높은 → 낮은 = **위협 지점** (예: S 정보를 O 생성형 AI에 업로드). = BLP의 No Write Down과 같은 생각

## 적용 절차 5단계 (137 나)
| 단계 | 할 일 |
|---|---|
| ① 준비 Prepare | 업무·업무정보·정보시스템·정보서비스 식별 |
| ② 등급분류 Categorize | 업무정보 → 정보시스템 C/S/O |
| ③ 위협식별 Identify | 「위치-주체-객체」 모델링, 높은→낮은 이동 지점 |
| ④ 보안대책 수립 Select | 보안통제 선택·조정, 구현계획 |
| ⑤ 적절성 평가·조정 Assess | 평가·보완·승인 → 국정원 보안성 검토 |

## 보안통제 6대 항목
권한 · 인증 · 분리·격리 · 통제 · 데이터 · 정보자산

## 추진 배경 (Ⅰ장 재료)
- 2006~ 망분리 → 원격근무·클라우드·생성형 AI 확산으로 업무 효율·데이터 활용 한계 → 업무 중요도에 따라 차등

## 고려사항 — 학원 틀 (137 다)
- 기술적–모델링: 등급별 차등 통제, 레거시 호환(망연계 장비, 점진 이관)
- 기술적–보안: MFA·최소 권한, 암호화·프로세스 격리·화이트리스트
- 관리적–프로세스: 5단계 산출물 관리, 책임자(CISO), 자체 심의위원회
- 관리적–거버넌스: 법령·예산·인력, 교육·훈련
- 교재 추가: 다 S·C로 올리면 망분리로 회귀 / 생성형 AI·SaaS 연계 구간 통제가 핵심

- 설계 패턴: 최소화=수집 최소화·가명화, 숨기기=암호화, 총계화=k-익명성·차등 프라이버시, 정보제공=유출 알림, 통제=사용자 중심 ID, 집행=접근통제, 입증=감사기록
- PbD vs 개인정보보호법 제3조: 설계 초기 내재화·사전예방·설계 주체 책임 ↔ 전 단계 정보주체 권리 보호·처리자 책임

## ⚠️ 개인정보 안심구역 vs 데이터안심구역 (136)
| 구분 | 개인정보 안심구역 | 데이터안심구역 |

# F. 유출사고형 (138컴 3교시)

## 학원 답 틀
- 가. ISMS-P 문제점 – 구조: 자율 인증(의무 아님), 인증 범위 임의 설정, 사후심사 부실(1인·1일), 인증 취소 미비(면죄부)
- 가. ISMS-P 문제점 – 수행: 서면 위주, 샘플링·스냅샷 점검, 정적 설정 위주, 신기술 위협 지체, 심사원 역량 격차
- 참고: ISMS-P 101개 = 관리체계 16 + 보호대책 64 + 개인정보 처리단계 21 (ISMS 80개)
- 나. PET 한계: 원본 직접 사용·비식별 미흡, 최소 이용 미준수, 단일 유출 피해 증폭, 데이터 단위 통제 부재, 처리 환경 분리 미흡, 내부자 이상행위 탐지 곤란
- 다. 대응: 원본 사용 제한 + PET 비식별, 최소권한(RBAC/ABAC)·데이터 단위 통제, 환경 분리, UEBA·DLP 실시간 탐지 → 정부 방향: '자율·서면' → '의무·실증'

| 사례 문장 | 한계 | 보완 |
|---|---|---|
| 테스트·분석 환경에서 원본 사용 | PET 미적용 | 가명처리·합성데이터 |
| 내부 접근통제 미흡 | 권한 과다·누적 | 최소 권한, 제로트러스트 |
| 로그는 있으나 실시간 탐지 실패 | 수집만 | SIEM·UEBA·SOAR |
| ISMS-P 인증 취득 상태 | 시점 점검 | 상시 점검, 내부 감사 |

# G. SBOM · 공급망

## 쉽게 먼저 (SBOM)
과자 봉지 뒤의 **성분표**예요. 2021년 Log4j가 터졌을 때 다들 "우리 시스템에 Log4j가 있나?"를 몰라 며칠씩 헤맸어요. SBOM은 SW에 어떤 부품이 몇 버전으로 들어 있는지 적은 성분표예요.

기출: 131회 1교시 · 134컴 1교시 · 134회 3교시(가. 오픈소스 취약점 / 나. SBOM 기반 관리 방안) · 136회 4교시(공급망 + 제로트러스트 아키텍처)

## 정의 (SBOM)
- 교재: SW 구성 컴포넌트·버전·라이선스·의존 관계를 기계가 읽을 수 있게 기록한 SW 구성 명세서
- ⚠️ 학원: 소프트웨어 컴포넌트 및 구성 요소를 식별할 수 있는 메타데이터와 저작권 및 라이선스 등 소프트웨어 콘텐츠에 대한 정보를 포함하는 공식 SW 자재 명세서

## 등장 배경 (SBOM)
SolarWinds(2020) · Log4Shell(2021) · XZ Utils(2024) / 미국 행정명령 14028(2021.5) · NTIA 최소요소(2021.7) / EU CRA / 국내 SW 공급망 보안 가이드라인 1.0(2024.5)

## NTIA 최소 요소 3영역 + 필드
- 데이터 필드 · 자동화 지원(SPDX·CycloneDX·SWID) · 관행·프로세스(Frequency·Depth·Known Unknowns·Distribution·Access Control·Accommodation of Mistakes)
- 필수 필드 7: 공급자명 · 컴포넌트명 · 버전 · 고유 식별자(PURL·CPE) · 의존 관계 · SBOM 작성자(국내 가이드: 저작권자) · 타임스탬프
- 134컴 Baseline 8: + Component Hash(무결성)

## 표준 포맷
| 포맷 | 만든 곳 | 강점 |
|---|---|---|
| SPDX | 리눅스 재단 (ISO/IEC 5962) | 라이선스·저작권 |
| CycloneDX | OWASP | 보안·취약점, VEX |
| SWID | ISO/IEC 19770-2 | 설치 SW 식별 |

## 오픈소스 취약점 (134 가) — 학원 틀
- 관리적: OSS 사용 현황 부재, 맹목적 사용·타이포스쿼팅, 점검 프로세스 부재 / 패치 지연, 조치 주체 모호
- 기술적: 소스 공개로 제로데이, 악성코드 삽입·크립토재킹 / 자체 조치 불가, 패치 호환성
- (교재: 알려진 취약점 방치 · 전이적 의존성 · 악성 패키지 · 메인테이너 침해(XZ) · 라이선스 위반 · 유지보수 중단)

## SBOM 기반 관리 방안 (134 나)
- 교재 생명주기: ① 생성(CI/CD·SCA) → ② 검증(서명) → ③ 공유 → ④ 취약점 DB 연계(NVD·CVE) → ⑤ 영향 판단(VEX) → ⑥ 정책·거버넌스(OSPO)
- 학원 틀: 관리적(SBOM 관리정책·R&R / 관리 절차) · 기술적(관리 속성 정의, 정적 분석·종속성 분석 툴) · SW 공급망(공급사·운영사 유통 체계) → 오픈소스 거버넌스

## 공급망 보안 (136) — 학원 틀
- 정의: HW·SW·서비스 등 외부 공급자의 제품·서비스가 도입되는 과정의 보안 위협을 식별·관리하는 보안 활동
- 필요성: 기술(외부 의존성 통제, 탐지·대응 자동화) / 관리(책임 범위, 사후 감사, 공급자 신뢰성 평가)
- C-SCRM: 레벨1 전사 · 레벨2 프로세스 · 레벨3 운영
- 참여자: 개발사(개발·빌드·배포 보안) / 공급사(제품 검증, 취약점 통보) / 운영사(요구사항, 인수테스트)
- SBOM 활용: SCA로 생성 → CVE·KEV·NVD 비교 → 우선순위 → 위험도 → 개선·공유

## 제로트러스트 기반 공급망 아키텍처 (136)
| 구간 | 적용 |
|---|---|
| 소스 코드 | 개발자 MFA, 최소 권한, 커밋 서명 |
| 빌드 | 격리된 빌드, 출처 증명(SLSA) |
| 아티팩트 | 코드 서명, SBOM 첨부 |
| 배포 | PDP/PEP가 서명·SBOM·취약점 검사 통과한 것만 |
| 서드파티 | JIT 접근, 세션 단위, 접근 기록 |
| 운영 | 런타임 모니터링, 자동 차단 |

- 학원 기술요소: 사용자·디바이스(MFA, EDR/XDR) / 데이터·네트워크(DLP/DRM, 마이크로 세그멘테이션) / 접근 관리(ABAC, SDP) / 자동화·모니터링(SOAR, SBOM)
- 핵심 문장: "공급망의 어느 단계도 기본 신뢰하지 않고, 단계마다 신원과 무결성을 검증한다"
