# 파인튜닝 · RAG · Advanced RAG — 대화 기반 학습정리

- **학습 날짜:** 2026-11-16 (KST)
- **과목:** AI
- **범위:** Fine-tuning → RAG → Advanced·Modular·Agentic RAG → AI 윤리기준(2020·2026) → AI 거버넌스(이후 학습 추록 포함)
- **문서 성격:** GPT가 오늘 실제 설명한 내용을 학습용으로 복원·정돈한 보충 MD. 별도의 AI 종합교재나 전체 일일 학습일지와 구별한다.
- **기록 원칙:** 실제로 답한 내용과 설명을 듣고 이해한 내용을 구분했다. 아래에 나온 내용이 모두 독립 인출·암기되었다는 뜻은 아니다.

# Ⅰ. 전체 핵심 — 사람말로 먼저 이해하기

회사 서버 운영 매뉴얼이 수천 페이지 있다고 가정한다. AI에게 **“RHEL 서버 패치 절차를 알려줘”**라고 물었을 때, AI가 답을 제대로 하게 만드는 방법에는 크게 두 가지가 있다.

- **Fine-tuning(파인튜닝):** AI 직원에게 회사의 보고서 양식과 업무 수행 방식을 **추가로 훈련**한다. 학습하면서 **모델 가중치가 변경**된다.
- **RAG(검색 증강 생성):** AI 직원이 회사의 최신 운영 매뉴얼을 **검색해 읽고 답변**한다. 보통 **생성 LLM의 가중치는 변경하지 않는다.**

> **딱 한 문장으로 구분**  
> 파인튜닝은 **모델 자체를 조정**하고, RAG는 **외부 지식을 검색해서 프롬프트에 넣어 활용**한다.

이 두 기법은 상호 배타적이지 않다. 회사 용어와 응답 형식을 Fine-tuning으로 익힌 모델이 최신 매뉴얼은 RAG로 찾아 답할 수 있다.

# Ⅱ. Fine-tuning(파인튜닝)

## 1. 사람말 원리

이미 일반적인 언어 능력을 가진 AI 모델이 있다. 그런데 회사 장애 보고서는 반드시 ‘장애 원인 → 영향 범위 → 조치 → 재발 방지’ 형식으로 작성해야 한다면? 해당 회사의 좋은 보고서 사례를 이용해 모델을 **추가 학습**시키는 방식이 Fine-tuning이다.

책을 찾게 하는 게 아니라, **모델의 답변 습관·표현·특정 작업 수행 능력** 등을 추가 훈련으로 조정한다.

## 2. 기술사 정의

**사전학습 모델을 도메인 데이터로 추가 학습하여 모델 가중치를 조정하는 기술**

- 목적: 특정 도메인·태스크에서 성능 향상 및 응답 형식·행동 적응
- 대상: 사전학습된 모델
- 수단: 추가 학습 데이터 및 학습 알고리즘
- 결과: **가중치(Parameters) 변화**

## 3. 구성도

```text
[사전학습 언어모델]         [도메인 학습 데이터]
          │                        │
          └──────────┬─────────────┘
                     ▼
              [추가 학습]
            손실 계산·역전파
                     │
                     ▼
              [가중치 조정]
                     │
                     ▼
            [특화된 모델]
                     │
                     ▼
          [질문 → 모델 직접 응답]
```

## 4. 주요 구성요소·특징

| 요소 | 역할 / 핵심 |
|---|---|
| 사전학습 모델 | 범용 언어 능력 보유 |
| 도메인 데이터셋 | 전문 용어, 작업 사례, 바람직한 답변 형식 제공 |
| 학습 방식 | 추가 데이터로 모델을 최적화 |
| 파라미터/가중치 | 학습에 따라 일부 또는 전체 값이 변함 |
| 평가·검증 | 정확성, 형식 준수, 과적합·편향 등을 검증 |

### 대표 기법

- **Full Fine-tuning:** 모델의 많은 또는 전체 가중치를 업데이트. 비용·자원 요구가 큼.
- **PEFT(Parameter-Efficient Fine-Tuning):** 일부 파라미터 또는 소규모 추가 모듈만 학습해 자원을 절약.
- **LoRA(Low-Rank Adaptation):** 가중치 변경을 저랭크 행렬의 학습으로 효율화하는 PEFT 기법.
- **QLoRA:** 양자화된 기반 모델에 LoRA를 결합하여 메모리 사용량을 낮추는 방식.
- **Instruction Tuning:** 지시-응답 데이터를 활용해 지시 수행에 맞게 모델을 조정.
- **RLHF:** 인간 선호 피드백을 활용하는 정렬(alignment) 방식. 단순히 Fine-tuning과 동의어는 아니며, 모델 조정 과정의 한 형태로 구분한다.

## 5. 강점과 한계

**강점:** 일관된 답변 스타일, 특정 업무 수행 능력, 도메인 표현 적응에 유리.  
**한계:** 학습 데이터 품질에 좌우되고, 학습·검증 비용이 들며, 최신 지식을 갱신하려면 재학습 등이 필요할 수 있음. 과적합, 망각, 학습 데이터 누출 등도 고려해야 함.

> **시험 포인트:** Fine-tuning은 **외부 문서를 매 질문마다 검색하는 방식이 아니다.** 모델의 내부 파라미터를 추가 학습으로 조정한다는 점이 핵심이다.

# Ⅲ. RAG(Retrieval-Augmented Generation, 검색 증강 생성)

## 1. 사람말 원리

RAG는 **AI 직원이 문제를 받으면 도서관에서 관련 매뉴얼을 찾아 읽은 뒤 답하게 하는 시스템**이다.

예를 들어 회사에 RHEL 서버 매뉴얼 1,000개가 있을 때, RAG는 질문에 관련된 매뉴얼 조각을 검색하여 LLM에게 참고자료로 전달한다.

- 검색에 쓰이는 문서는 **외부 지식**이다.
- 검색 결과를 **프롬프트에 추가**한다.
- LLM은 질문과 참고자료를 함께 보고 **응답을 생성**한다.
- 통상 이 과정 자체가 **LLM 가중치를 재학습시키지는 않는다.**

## 2. 기술사 정의

**외부 지식을 검색하여 프롬프트에 결합하고 LLM의 근거 기반 응답 생성을 지원하는 기법**

RAG = **Retrieval(검색) + Augmentation(증강) + Generation(생성)**

## 3. 문서를 미리 준비하는 과정 — 인덱싱(Indexing)

운영 매뉴얼 PDF 1,000개를 그대로 LLM에 한꺼번에 넣는 것이 아니다. 찾기 쉬운 형태로 먼저 정리한다.

```text
[PDF·업무문서 수집]
         │
         ▼
[텍스트 추출·전처리]
         │
         ▼
[청킹(Chunking)]   ── 긴 문서를 작은 문맥 단위로 분할
         │
         ▼
[임베딩(Embedding)] ─ 텍스트 의미를 고차원 수치 벡터로 변환
         │
         ▼
[검색 인덱스 저장] ── 예: 벡터 DB + 원문 위치·메타데이터
```

**중요한 보충:** PDF를 텍스트로 추출해야 한다. 스캔 PDF라면 별도의 텍스트 인식이 필요할 수 있다. 문서의 출처, 버전, 페이지 같은 메타데이터도 유지하면 검색 품질과 근거 추적에 도움이 된다.

### 3-1. 청킹(Chunking)

- 긴 문서를 작은 조각(Chunk)으로 나누는 기술.
- 문서 전체가 너무 길어 검색·전달하기 곤란할 때 유용.
- 조각 크기가 너무 작으면 문맥을 잃고, 너무 크면 관련 없는 내용이 섞일 수 있음.
- 필요에 따라 청크 간 중첩(Overlap)을 사용.

> **암기:** 청킹 = 문서 분할.

### 3-2. 임베딩(Embedding)

- 텍스트의 **의미적 특징을 고차원 수치 벡터(Vector)**로 변환.
- 예시: `"리눅스 서버 패치" → [0.81, 0.23, -0.45, ...]` (숫자는 설명용 가상값)
- 사용자 질문도 같은 검색 체계에서 임베딩하여 문서 벡터와 비교할 수 있다.
- 임베딩 변환에 쓰이는 함수는 보통 **학습된 신경망 임베딩 모델**이다.
- **함수로 변환한다(X). 함수를 통해 수치 벡터로 변환한다(O).**

#### 학습 중 나왔던 코끼리 비유

학생: **"AI는 수학적으로 코끼리를 냉장고에 넣을 수 있겠다"** 🐘

코끼리 자체를 냉장고에 넣는 것이 아니라, **'코끼리'의 의미를 표현하는 벡터 데이터를 저장**하는 것은 가능하다. 이것이 사물이나 언어의 특징을 수학적 공간에 나타내는 **표현 학습(Representation Learning)**과 연결된다.

- `코끼리`와 `아기 코끼리`는 의미가 비슷하므로 잘 학습된 임베딩 공간에서는 가까운 표현을 가질 가능성이 높다.
- 이때 '가깝다'는 것은 유클리드 거리 등 거리 척도일 수도 있고, **벡터의 방향 유사성**일 수도 있다.

학생이 설명한 핵심 문장:
> "비슷한 개념이 수없이 많은 차원의 공간에서 가까운 곳에 위치한다."

기술사 문장으로 다듬으면:
> **의미적으로 유사한 데이터는 고차원 임베딩 공간에서 가까운 벡터로 표현되며, 벡터 간 유사도를 계산하여 관련 정보를 검색한다.**

### 3-3. 벡터 DB(Vector Database)

- 임베딩 벡터와 원문/출처 연결정보를 저장·색인해 유사도 검색을 지원.
- **RAG가 반드시 벡터 DB를 요구하는 것은 아니다.** BM25 등 키워드 검색이나 다른 검색 인덱스로도 RAG를 구현할 수 있다.
- **벡터 DB 자체가 문서를 이해해 자연어 답변을 생성하는 AI인 것은 아니다.**

### 3-4. 코사인 유사도(Cosine Similarity)

두 벡터의 **방향이 얼마나 비슷한지** 측정하는 대표적인 기법.

\[
\operatorname{sim}(A,B)=\frac{A\cdot B}{\lVert A\rVert\lVert B\rVert}
\]

| 값 | 뜻 |
|---|---|
| +1 | 같은 방향 |
| 0 | 서로 수직 |
| -1 | 반대 방향 |

문서 임베딩에서 이 수치가 실제 의미적 관련성을 어느 정도 반영하는지는 **임베딩 모델과 데이터**에 따라 달라진다. 코사인 유사도는 여러 유사도/거리 척도 중 하나다.

## 4. 질문을 처리하는 과정 — RAG의 4단계

```text
                   [사전 작업]
           ① 인덱싱(Indexing)
문서 → 텍스트 추출 → 청킹 → 임베딩 → 인덱스 저장

                   [질문 발생]
질문: "RHEL 서버 패치 절차 알려줘"
                      │
                      ▼
             ② 검색(Retrieval)
   질문 임베딩 → 유사 문서 검색 → 관련 조각 추출
                      │
                      ▼
            ③ 증강(Augmentation)
     [사용자 질문] + [검색된 매뉴얼 조각]
              → 프롬프트 구성
                      │
                      ▼
             ④ 생성(Generation)
        LLM이 참고자료를 읽고 답변 생성
```

**중요:** 인덱싱은 보통 문서 등록 시 미리 수행한다. 사용자가 질문할 때마다 전체 문서를 재청킹하는 것은 일반적인 구성은 아니다.

### 검색 후 정확히 무엇을 하는가?

사용자 질문: `RHEL 서버 패치 절차 알려줘.`  
검색된 문서: `사내 RHEL 운영 매뉴얼 — 패치 절차 발췌`  
프롬프트: `사용자 질문 + 검색된 매뉴얼 + 답변 지침`  
LLM: 이를 참고해 설명과 근거를 생성.

> **핵심:** RAG에서 문서 검색만으로는 끝나지 않는다. **검색 → 프롬프트 증강 → 생성**이 이어져야 전체 RAG라고 부른다.

## 5. RAG에서 실제로 AI가 하는 일

| 단계 | AI 필요 여부 | 설명 |
|---|---|---|
| 문서 수집·청킹 | 필수 아님 | 일반 프로그램으로 처리 가능 |
| 임베딩 | 통상 AI 모델 사용 | 학습된 신경망으로 의미 벡터 생성 |
| 벡터 유사도 계산 | 필수 아님 | 수학적 거리·유사도 알고리즘 |
| 키워드 검색 | 필수 아님 | BM25 등 전통 정보검색 기법 |
| 프롬프트 결합 | 필수 아님 | 질문과 검색문서를 조합하는 프로그램 |
| 답변 생성 | **생성형 AI 사용** | LLM이 문맥을 해석하고 문장 생성 |

따라서 **RAG 자체는 단일 AI 모델이 아니라 검색 시스템과 생성형 AI를 결합한 아키텍처/기법**이다. 임베딩 모델도 AI이고, 생성 LLM도 AI일 수 있다.

## 6. RAG의 강점과 한계

### 강점

- 최신 외부 문서를 활용할 수 있음.
- 문서 출처를 함께 제시하도록 구성할 수 있음.
- 매번 LLM의 가중치를 재학습하지 않고 정보 갱신 가능.
- 기업 내부 문서, 매뉴얼, 정책 등의 질의응답에 유용.

### 한계 — 왜 환각(Hallucination)이 완전히 사라지지 않는가?

1. **검색 오류:** RHEL 9를 물었는데 RHEL 8 문서 검색.
2. **원천 데이터 오류:** 매뉴얼이 오래되었거나 잘못 작성됨.
3. **생성 오류:** 정확한 문서를 찾았는데도 LLM이 내용을 잘못 해석.
4. **근거 부족:** 적절한 자료가 없는데도 그럴듯한 답을 만들어냄.
5. **보안 문제:** 검색된 문서의 악성 지시문(prompt injection), 권한 없는 문서 노출 등 관리 필요.

**RAG는 환각을 줄이기 위한 방법이지, 환각을 0으로 보장하는 기술이 아니다.**

# Ⅳ. Advanced RAG — 검색 품질을 높이기

기본 RAG가 관련 문서를 찾아 LLM에 넣는다면, **Advanced RAG는 검색·선정·검증 등을 개선해 더 적절한 문서를 제공**하는 구성이다. 오늘 대화에서는 특히 아래 세 가지를 학습했다.

## 1. Re-ranking(재순위화)

### 사람말 원리

검색 결과 20개를 받아도 상위 1개가 반드시 가장 정확한 문서는 아닐 수 있다. 후보를 먼저 찾은 뒤 **질문과 문서의 관련성을 정밀하게 다시 평가하여 순위를 재조정**하는 것이 재순위화다.

### 실제 예

질문: `RHEL 9 보안 패치 절차`

| 최초 검색 순위 | 문서 | 재평가 관점 |
|---|---|---|
| 1위 | RHEL 8 일반 패치 매뉴얼 | 버전과 범위가 맞지 않음 |
| 2위 | **RHEL 9 보안 패치 매뉴얼** | 질문에 가장 적합 |
| 3위 | RHEL 9 서버 설치 가이드 | 버전은 맞지만 작업이 다름 |

Re-ranking 후 **2위 문서가 1위가 될 수 있다.**

- 기본 검색: 관련 후보를 **빠르게** 확보.
- 재순위화: 후보의 **정확한 관련성**을 추가 평가.

> **정의:** 1차 검색된 후보 문서의 질의 관련성을 재평가하여 검색 순위를 조정하는 기술.

## 2. Metadata Filtering(메타데이터 필터링)

문서에 붙은 **OS 버전, 제품, 날짜, 문서 유형, 권한 등 구조화된 속성**을 조건으로 검색 범위를 제한하는 방법.

### RHEL 매뉴얼 예

| 문서 | OS 버전 | 문서 종류 |
|---|---|---|
| A | RHEL 8 | 패치 |
| B | **RHEL 9** | **보안 패치** |
| C | RHEL 9 | 설치 |
| D | RHEL 7 | 보안 패치 |

질문이 `RHEL 9 보안 패치 절차`라면 `OS 버전 = RHEL 9` 조건을 이용해 RHEL 7·8 자료를 제외한다. 추가로 문서 유형을 활용할 수도 있다.

**핵심:** 내용의 의미 유사성만 믿지 말고, **버전처럼 정확해야 하는 속성**은 조건으로 제한할 수 있다.

주의: 메타데이터가 누락·오입력되었으면 적합한 문서가 제외될 수 있으므로 관리가 필요하다.

## 3. Hybrid Search(하이브리드 검색)

**키워드 기반 검색 + 의미 기반 벡터 검색**을 결합하는 방식.

| 방식 | 대표 예 | 장점 | 주의점 |
|---|---|---|---|
| 키워드 검색 | BM25 | 정확한 식별자·제품명·버전 검색에 유리 | 표현이 다르면 놓칠 수 있음 |
| 벡터 검색 | Embedding + 유사도 | 비슷한 의미·다른 표현 검색에 유리 | 정확한 버전이나 식별자를 혼동할 수 있음 |
| **하이브리드 검색** | 양쪽 결과 결합 | 정확 일치와 의미 검색의 장점을 조합 | 점수 결합·중복 제거 설계 필요 |

예: `보안 업데이트`와 `패치`는 의미가 유사하지만, `RHEL 8`과 `RHEL 9`는 정확히 구분해야 한다. 두 관점을 함께 활용하는 것이 유리할 수 있다.

## 4. 세 기법 연결 구성도

```text
[질문: RHEL 9 보안 패치 절차]
               │
               ▼
[메타데이터 필터링: OS 버전=RHEL 9]
               │
               ▼
[하이브리드 검색: BM25 + 벡터 검색]
               │
               ▼
[Re-ranking: 문서 관련성 재평가]
               │
               ▼
[상위 관련 문서 → 프롬프트 증강 → LLM 생성]
```

**설계 주의:** 위 순서는 하나의 **예시 구성**이다. 모든 Advanced RAG가 세 요소를 반드시 사용하거나 이 순서만 따르는 것은 아니다.

## 5. 기본 RAG와 Advanced RAG 비교

| 구분 | 기본 RAG | Advanced RAG(오늘 학습 범위) |
|---|---|---|
| 핵심 | 문서 검색·증강·생성 | 검색·선정 품질 추가 최적화 |
| 검색 방식 | 단일 벡터/키워드 검색 가능 | 하이브리드 검색 활용 가능 |
| 문서 범위 | 전체 인덱스 검색 가능 | 메타데이터 조건으로 제한 가능 |
| 검색 순위 | 초기 점수 기반 | Re-ranking으로 재정렬 가능 |
| 장점 | 구성 단순, 구축 용이 | 관련성·정확성 향상 가능 |
| 단점 | 오검색·부적절한 근거 | 복잡성·지연·운영비용 증가 가능 |

**당시 상태:** 여기까지 설명했을 때는 Modular RAG 본학습 전이었다. **이후 학습한 내용은 아래 Ⅺ장에서 보충**한다. 전체 답안 인출·백지는 여전히 미확인이다.

# Ⅴ. Fine-tuning vs RAG — 최종 비교표

| 비교 관점 | Fine-tuning | RAG |
|---|---|---|
| 목적 | 모델의 업무 수행·답변 방식 적응 | 외부 지식을 활용한 근거 기반 답변 |
| 핵심 원리 | 추가 학습 | 검색 + 프롬프트 증강 + 생성 |
| 모델 가중치 | **변경** | **일반적으로 변경하지 않음** |
| 정보 출처 | 학습 데이터에 반영된 패턴 | 검색 시점의 외부 문서 |
| 최신성 반영 | 재학습·모델 조정 필요할 수 있음 | 인덱스/문서 갱신으로 반영 가능 |
| 구성 요소 | 데이터셋·학습 절차·모델 | 문서 인덱스·검색기·프롬프트·LLM |
| 비용 중심 | 학습·검증 비용 | 검색 인프라·추론·지연 비용 |
| 환각 위험 | 여전히 존재 | 여전히 존재. 검색 오류도 영향 |
| 활용 | 업무 형식 통일, 특정 태스크 특화 | 운영 매뉴얼, 사내 규정, 최신 자료 Q&A |
| 대표 관련 기술 | LoRA·QLoRA·PEFT | 청킹·임베딩·BM25·벡터 DB·Re-ranking |
| 결합 가능 여부 | RAG와 함께 사용 가능 | Fine-tuned 모델을 생성에 사용 가능 |

## 어느 것을 쓸까?

- **"장애 보고서를 항상 회사 양식으로 작성해 줘"** → Fine-tuning 검토.
- **"이번 달 최신 패치 공지를 반영해서 답해 줘"** → RAG 검토.
- **"회사 양식으로, 최신 매뉴얼을 근거로 답해 줘"** → Fine-tuning + RAG 결합 검토.

> **기술사 단골 차이:** **Fine-tuning = 가중치 조정 / RAG = 외부지식 검색·프롬프트 결합**.

# Ⅵ. 이번 대화에서 실제 나온 질문·인출·오답

아래는 **실제로 말한 것만** 기록했다. 학습자료를 보고 답한 경우 독립 인출로 평가하지 않는다.

| 질문 또는 상황 | 학생의 실제 답변·질문 | 평가와 보완 |
|---|---|---|
| Fine-tuning과 RAG의 차이 | `가중치. 검색도구` | **핵심 정답.** FT는 가중치 수정, RAG는 외부 지식 검색 후 프롬프트 결합으로 구체화 |
| RAG 문서 등록 | `그냠 검색하는거 아니야? 벡터db에 등록해야돼?` | RAG에 벡터 DB는 필수가 아님을 설명. 벡터형 RAG에서는 청킹·임베딩·인덱스가 일반적 |
| 임베딩 결과 | `함수로?` | **오답.** 함수는 변환 수단, 결과는 수치 벡터 |
| 임베딩 결과 재확인 | `숫자벡터` | **정답.** 다만 이전 설명·교정 후 답한 결과 |
| 긴 문서 분할 | `청킹?` | **정답.** 바로 앞 설명을 본 상태의 인출 |
| 문서 검색 후 처리 | `몰라?` | 처음에는 알지 못함. 검색결과를 프롬프트에 넣는 원리 설명 |
| 검색 문서 전달 위치 | `프롬프트에` | **정답.** 설명 직후 확인 |
| RAG 전체 순서 | `문의 청킹 임베딩, 검색, 프롬프트에 추가, 답변` | **주요 흐름 인출 성공, 일부 누락.** 텍스트 추출·벡터 DB 저장·질의 임베딩을 보완 |
| RAG가 환각을 완전히 제거하는지 | `아니니까 물어보는거 같은데?` | 결론은 맞지만 **이유는 인출하지 않음**. 검색·데이터·생성 오류를 배움 |
| 정확한 문서를 검색했는데 답변을 틀린 경우 | `생성의` | **정답.** 생성 단계 오류를 구별함 |
| RAG가 AI 자체인지 | `rag는 AI를 사용하는 기술이 아니라, AI가 사용하게하는 기술이야?` | 좋은 원리 질문. RAG는 단일 모델이 아닌 검색+생성 아키텍처임을 설명 |
| 임베딩의 의미 공간 | `와그럼 AI는 수학적으로 코끼리를 냉장고에 넣울수 있겠다` | **이해를 보여 주는 비유.** 벡터 표현과 물체 자체는 다름 |
| '코끼리'와 '아기 코끼리' 벡터 | `가가울껄 비슷한개념이 수없이많은 차원의 공간에 가까운돗에 위치한다` | **원리 설명 성공.** 고차원 임베딩 공간·의미 유사성 이해 |
| 유사도 측정 기법 | `보고 말하는건게 코사인유사도?` | **자료 참고 정답. 독립 인출로 계산하지 않음.** |
| 재순위화 역할 | `순위라매?` | 용어 자체에 답이 제시되어 있었음. **독립 인출 판정 보류** |
| RHEL 9 오검색 개선 | `몰랑` | 당시 미학습. **메타데이터 필터링, 하이브리드 검색** 이후 설명 |
| Windows 2022/2019 구분 문제 | 아직 답하지 않음 | 다음 복습용으로 남김. 미응답을 정답 처리하지 않음 |

**평가:** 파인튜닝 vs RAG의 핵심 구분과 RAG의 큰 처리 흐름은 말로 답했다. 다만 전체 기술사 답안(정의·구성도·비교표)을 백지 작성한 기록은 없으며, Advanced RAG의 독립 인출도 아직 확인되지 않았다. **이 문서만으로 장부의 확인수준 3 또는 완전한 2를 부여하지 않는다.**

# Ⅶ. 반드시 외울 핵심 키워드

## 1. Fine-tuning

**사전학습 모델 / 도메인 데이터 / 추가 학습 / 가중치 조정 / PEFT / LoRA / QLoRA / 평가·검증**

## 2. RAG

**외부 지식 / 검색 / 프롬프트 증강 / LLM 생성 / 근거 기반 응답 / 가중치 미변경**

## 3. RAG 인덱싱

**문서 수집 / 텍스트 추출 / 청킹 / 임베딩 / 벡터 인덱스 / 메타데이터**

## 4. 벡터 검색

**고차원 수치 벡터 / 의미 유사성 / 코사인 유사도 / 질의 임베딩 / 유사 문서 추출**

## 5. Advanced RAG

**메타데이터 필터링 / BM25 / 벡터 검색 / 하이브리드 검색 / Re-ranking**

## 6. 비교표 암기 축

**목적 / 원리 / 가중치 / 지식 갱신 / 구성요소 / 비용 / 정확성·환각 / 적용**

**주의:** 이 파일은 **새로운 두음을 임의 확정하지 않았다.** 이미 확정된 암기 두음이 있는지 공동 장부와 대조한 뒤 사용한다.

# Ⅷ. 다음 복습: 한 번에 한 문제씩 인출

1. **Fine-tuning과 RAG의 차이를 '가중치'와 '외부 지식' 관점에서 설명하라.**
2. **RAG의 4단계(인덱싱·검색·증강·생성)와 세부 구성요소를 말하라.**
3. **청킹과 임베딩의 차이를 정의하라.**
4. **임베딩과 벡터 DB 없이도 RAG를 만들 수 있는지 근거를 설명하라.**
5. **코사인 유사도를 외우지 않고 개념부터 설명하라.**
6. **RAG의 환각이 사라지지 않는 이유를 검색·데이터·생성 단계로 나누어 설명하라.**
7. **RHEL 9 보안 패치 관련 문서를 고르는 방법을 메타데이터 필터링·하이브리드 검색·Re-ranking 관점에서 비교하라.**
8. **Windows Server 2022 장애 복구 질의에서 2019 문서를 제외하는 조건을 설계하라.**

처음 작성 당시 다음 연결 토픽은 **Modular RAG·AI 윤리·LLM 보안**이었다. **이후 Modular·Agentic RAG 및 AI 윤리·거버넌스는 아래 추가 학습에 반영**했다. LLM 보안은 아직 본학습 전이다.

# Ⅸ. 다음 AI에게 인수인계

- 학생은 운영 매뉴얼 비유(RHEL 패치, 버전이 다른 문서)를 통해 RAG를 이해했다. 향후에도 **서버 인프라 실무 예시**를 쓰는 것이 효과적이다.
- **핵심 이해:** Fine-tuning은 가중치 조정, RAG는 외부 지식 검색 및 프롬프트 증강. RAG가 단일 AI 모델인지 스스로 질문하며 시스템 아키텍처라는 점까지 연결했다.
- **특히 좋은 사고:** 임베딩을 통해 의미가 고차원 공간에 배치된다는 표현을 스스로 만들어 냈으며, '코끼리를 수학적으로 냉장고에 넣는다'는 비유로 표현 학습과 저장의 차이를 탐색했다.
- **취약점:** 인덱싱과 질의 시 처리의 구분, 코사인 유사도 독립 인출, Advanced RAG 구성요소의 독립 인출. 검색된 문서를 프롬프트에 넣는다는 점은 설명 이후 답했다.
- **진행상 주의:** 학생은 정답이 이미 들어간 질문을 싫어한다. 뜻이 드러나는 용어를 바로 따라 말하게 하기보다 **현장 상황에서 원인·해결 방법을 스스로 선택**하도록 질문할 것. 한 번에 하나씩.
- **다음 시작 질문:** “Windows Server 2022 장애 복구를 찾을 때 2019 매뉴얼을 제외하려면 문서의 어떤 속성에 어떤 조건을 걸어야 할까?”
- **초기 작성 시 미완료:** Modular RAG 상세 원리, Advanced RAG 백지 답안, RAG/Fine-tuning 비교표 백지 작성. 이후 Modular RAG 원리와 비교는 배웠으므로 **아래 추록의 최신 상태**를 따를 것. 백지 작성은 여전히 미확인.

# Ⅹ. 추가 학습 — Advanced RAG 완성 (기존 Ⅳ장 보충)

> **추록 작성 이유:** 원래 파일의 Ⅳ장에는 재순위화·메타데이터 필터링·하이브리드 검색 3가지까지만 있었다. 학생이 “그 외 구성 기술을 빠뜨리지 말고, Advanced → Modular → Agentic 순서로 한 토픽씩 정리해 달라”고 요청하여 이후 수업 내용을 추가한다. **강의를 듣거나 표를 본 것만으로 독립 인출 성공으로 처리하지 않는다.**

## 1. 사람말 원리와 정의

- **기본 RAG:** 매뉴얼을 찾아 LLM에게 읽혀 준다.
- **Advanced RAG:** 잘못된 버전·관련 없는 문서를 가져오는 문제를 줄이도록 **질문, 검색, 문서 선별, 근거 검증**을 개선한다.
- **기술사 정의:** **기본 RAG의 질의 처리·검색·증강·검증 과정을 고도화하여 검색 정확도와 응답 신뢰성을 향상하는 기술.**

## 2. 구성도 — 검색 전·검색·검색 후·생성

```text
[사용자 질문: "RHEL 9 보안 패치 절차"]
                     │
                     ▼
① 검색 전(Pre-Retrieval)
   [질의 재작성 / 질의 확장]
                     │
                     ▼
② 검색(Retrieval)
   [하이브리드 검색(BM25+벡터) / 메타데이터 필터링]
                     │
                     ▼
③ 검색 후(Post-Retrieval)
   [재순위화 / 문맥 압축]
                     │
                     ▼
④ 프롬프트 증강 → LLM 생성 → 답변 근거 검증
```

이 순서는 **대표적인 예시**이며, 모든 고급 RAG가 모든 모듈을 사용하거나 동일 순서로 실행하지는 않는다.

## 3. 구성 기술 8가지 — 시험 암기표

| 구간 | 핵심 기술(한글·영문) | 역할 | RHEL 패치 예시 |
|---|---|---|---|
| 검색 전 | **질의 재작성(Query Rewriting)** | 모호한 질문을 검색하기 좋게 변경 | 대화 문맥상 `서버 패치` → `RHEL 9 보안 패치 절차` |
| 검색 전 | **질의 확장(Query Expansion)** | 연관어·동의어를 더해 검색 누락 감소 | `업데이트`, `보안 패치`, `패키지 갱신` 포함 |
| 검색 | **하이브리드 검색(Hybrid Search)** | 키워드(BM25)와 벡터 의미 검색 결합 | `RHEL 9` 정확 일치 + `패치/업데이트` 의미 검색 |
| 검색 | **메타데이터 필터링(Metadata Filtering)** | 문서의 구조화된 속성 조건으로 범위 제한 | `OS 버전 = RHEL 9`로 RHEL 8 문서 제외 |
| 검색 후 | **재순위화(Re-ranking)** | 검색된 후보 문서의 관련성 정밀 재평가 | 2위의 RHEL 9 보안 매뉴얼을 1위로 올릴 수 있음 |
| 검색 후 | **문맥 압축(Context Compression)** | 불필요한 문장 제거·핵심 근거 추출 | 100쪽 문서에서 실제 패치 절차만 추림 |
| 생성 | **근거 기반 생성(Grounding)** | 검색 근거를 사용해 답변하도록 구성 | 패치 절차·출처 인용 |
| 검증 | **답변 검증(Answer Verification)** | 생성 답변과 검색 근거의 일치 여부 확인 | 문서에 없는 패치 명령이 삽입됐는지 점검 |

### 주요 특징
- 검색 정확도·관련성·문맥 품질을 높일 수 있다.
- 근거의 적합성을 높여 환각 위험을 낮추는 데 기여하지만 **환각 제거를 보장하지 않는다**.
- 추가 모델 호출, 검색·검증 단계로 **비용·지연·복잡도**가 증가할 수 있다.

## 4. 검색기(Retriever)와 재순위화 모델(Reranker)을 나누는 이유

```text
[매뉴얼 100만 건] ── 빠른 1차 검색 ──> [후보 50건]
                                             │
                                    정밀한 2차 재평가
                                             ▼
                                       [최종 5건]
                                             │
                                             ▼
                                       [생성 LLM]
```

*위 100만·50·5는 설명용 예시 숫자.*

- **1차 검색:** 사전 임베딩·검색 인덱스로 대량 문서에서 후보를 **빠르게** 찾는다. 중요한 근거를 놓치지 않도록 **재현율(Recall)** 확보에 주력한다.
- **2차 재순위화:** 소수 후보에 대해 질문과 문서를 함께 정밀하게 평가하고, 상위 문서의 **관련성·정밀도(Precision)** 향상을 도모한다.
- **한계:** 1차 검색에서 누락한 문서는 2차 재순위화가 **후보 외부에서 복구할 수 없다.** 따라서 후보 품질이 중요하다.
- **비유:** 100만 장의 이력서를 빠르게 추려 후보 50명을 만든 뒤 50명을 정밀 면접한다. 100만 명 모두를 정밀 면접하는 것은 느리고 비싸다.
- **주의:** 모든 구현에서 재현율과 정밀도가 깔끔하게 따로 분리되는 것은 아니다. 여기서는 설계상의 대표 목적을 구분한 것이다.

## 5. 개선 주체는 누군가?

Advanced RAG가 반드시 “별개의 AI 에이전트 여러 개”를 뜻하는 것은 아니다. **질의 재작성 모듈, 검색 알고리즘, 재순위화 모델, 생성 LLM, 전체 흐름 제어기**가 역할을 분담한다.

| 작업 | 구현 가능 방식 |
|---|---|
| 질문 재작성 | LLM 또는 규칙 기반 프로그램 |
| BM25/벡터 유사도 검색 | 전통 검색 알고리즘·벡터 인덱스 |
| 메타데이터 필터링 | 조건식·DB 검색 |
| 재순위화 | 별도 학습 모델(예: Cross-Encoder), LLM, 규칙 등 |
| 최종 답변 | 생성형 LLM |
| 단계 연결 | 오케스트레이터(흐름 제어 프로그램) |

**동일한 LLM을 두 번 호출할 수도 있다.** 첫 호출에서 질문을 재작성하고, 두 번째 호출에서 검색된 문서를 바탕으로 답변한다. **역할이 다르다고 모델까지 반드시 달라야 하는 것은 아니다.**

# Ⅺ. Modular RAG — 모듈형 검색 증강 생성

## 1. 사람말 원리 및 기술사 정의

Advanced RAG에 여러 기능이 생겼다면 매번 전체 시스템을 다시 만드는 대신 **검색·라우팅·결합·생성 기능을 레고 블록처럼 구성하고 교체**할 수 있다.

**기술사 정의:** **검색·라우팅·재순위화·생성 기능을 독립 모듈로 구성하여 필요에 따라 유연하게 조합·교체하는 RAG 아키텍처.**

## 2. 특징

- **모듈 독립성:** 개별 기능을 분리해 개발·교체.
- **유연한 조합:** 질의 유형별로 서로 다른 검색 경로 적용.
- **확장성·재사용성:** 새 검색기·데이터 소스·검증 모듈 추가.
- **운영 한계:** 모듈 간 인터페이스·데이터 형식·오케스트레이션·오류 추적이 복잡해진다.

## 3. 구성도

```text
                   [사용자 질문]
                         │
                         ▼
               [라우터 Router]
                   /           \
                  ▼             ▼
     [운영 매뉴얼 검색 모듈]   [장애 이력 DB 검색 모듈]
     (벡터 검색 등)          (SQL / BM25 등)
                  \             /
                   ▼           ▼
               [결과 결합 Fusion]
                         │
                         ▼
               [재순위화 모듈]
                         │
                         ▼
                 [생성 LLM]
         (전체 단계 연결: 흐름 제어기)
```

라우터가 한쪽만 선택하거나 여러 모듈을 병렬 호출할 수도 있다. 재순위화·필터링은 필요한 경우에만 넣는다.

## 4. 핵심 구성요소

| 구성요소 | 역할 |
|---|---|
| **라우터(Router)** | 질문을 보고 검색기·처리 경로 선택 |
| **검색 모듈(Retrieval Module)** | 벡터 DB·SQL·키워드 등 데이터 소스별 검색 |
| **결과 결합 모듈(Fusion Module)** | 여러 검색 결과 통합·중복 제거 |
| **재순위화 모듈(Re-ranking Module)** | 후보의 질문 관련성 재평가 |
| **생성 모듈(Generation Module)** | 선별된 근거를 바탕으로 답변 |
| **흐름 제어기(Orchestrator)** | 모듈 실행 순서·데이터 전달·오류 흐름 관리 |

**중요:** 모듈 자체는 **특정 기능을 수행하는 부품**이다. 모듈이 존재한다고 반드시 자율적 판단을 하는 AI 에이전트가 있는 것은 아니다. 규칙 기반 라우터만으로도 Modular RAG를 구현할 수 있다.

# Ⅻ. Agentic RAG — 에이전트형 검색 증강 생성

## 1. 사람말 원리 및 기술사 정의

기본 RAG가 한 번 검색하고 끝났다면, 복잡한 장애 질문에서 근거가 부족할 수 있다. **LLM 기반 에이전트가 '다른 DB도 찾아볼까?'라고 결정해 검색을 반복하거나 도구를 선택**할 수 있다.

**기술사 정의:** **AI 에이전트가 검색 계획·도구 활용·결과 평가·재검색을 자율적으로 수행하여 복잡한 질의에 대응하는 RAG 기술.**

## 2. 특징

- **계획(Planning):** 큰 질문을 하위 작업으로 분해.
- **도구 사용(Tool Use):** 벡터 검색기·SQL·API 등 외부 도구 호출.
- **자기 평가(Reflection/Evaluation):** 검색 근거의 충분성·정확성 점검.
- **반복 검색(Iterative Retrieval):** 결과가 부족하면 질의 수정·재검색.
- **한계:** 반복 호출에 따른 **지연·비용**, 잘못된 도구 선택, 에이전트의 오판, 권한 남용 가능성. **권한 최소화·반복 상한·로그·종료 조건** 필요.

## 3. 구성도

```text
[질문: "RHEL 9 패치 후 서비스가 안 올라와"]
                        │
                        ▼
               [AI 에이전트: 계획]
                        │
                        ▼
              [도구 선택 / 검색 실행]
                        │
                        ▼
               [근거 품질 자기 평가]
                    /       \
           [부족하다]       [충분하다]
              │                 │
        [질의 수정·재검색]   [LLM 최종 답변]
              └────── 반복 ─────┘
```

위 도식에서 '반복'은 **부족한 경우 다시 검색 단계로 돌아간다**는 뜻이며, 충분하면 응답을 생성한다.

## 4. 구성요소

| 구성요소 | 역할 |
|---|---|
| 계획기(Planner) | 작업 분해·검색 계획 수립 |
| 에이전트(Agent) | 현재 정보 평가 후 다음 행동 결정 |
| 도구 호출기(Tool Calling) | 검색·DB·API 호출 |
| 상태·기억(State/Memory) | 이전 검색 결과·진행 상황 유지 |
| 결과 평가(Reflection) | 자료 충분성·답변 품질 평가 |
| 반복 제어(Iteration Control) | 재검색·종료 조건 관리 |
| 생성기(Generator) | 근거 종합·최종 답변 |

**구별:** 같은 검색을 여러 번 실행한다는 사실만으로 반드시 Agentic이라고 단정하면 안 된다. **에이전트가 상황을 평가하여 다음 행동을 동적으로 결정한다**는 것이 핵심이다.

# ⅩⅢ. Advanced · Modular · Agentic RAG 최종 비교와 결합 관계

## 1. 시험용 비교표

| 비교 항목 | Advanced RAG | Modular RAG | Agentic RAG |
|---|---|---|---|
| 초점 | **품질 개선** | **기능 조합** | **자율 판단** |
| 핵심 질문 | 어떻게 더 잘 찾을까? | 기능을 어떻게 나눠 조립할까? | 다음에 무엇을 해야 할까? |
| 특징 | 검색 전·후 단계 고도화 | 기능의 독립성·교체 가능성 | 계획·도구 호출·반복 평가 |
| 대표 요소 | 재작성·하이브리드·필터·재순위화 | 라우터·검색 모듈·결합·생성 | 에이전트·플래너·도구·Reflection |
| 제어 | 설계된 파이프라인 중심 | 오케스트레이터·라우터 | 동적 의사결정·반복 |
| 장점 | 검색·근거 관련성 향상 | 재사용·확장·유지보수 | 다단계 문제 해결 유리 |
| 한계 | 지연·비용 증가 | 연동·인터페이스 복잡 | 오판·권한·종료·비용 관리 |

## 2. 세 개는 배타적인 종류가 아니라 서로 다른 관점

학생이 질문한 핵심:
> “Advanced에서 다른 기능이 검색을 개선하면 그게 모듈인 것 아닌가? Agentic의 에이전트가 개선된 검색 모듈을 스스로 선택해서 쓰면 세 가지가 동시에 성립하는 것 아닌가?”

**그렇다. 정확한 시스템 구조 추론이다.**

- **Advanced = 무엇을 개선하는가?** → 검색·응답 품질.
- **Modular = 어떻게 구성하는가?** → 독립 모듈과 조합.
- **Agentic = 누가 다음 행동을 결정하는가?** → AI 에이전트.

```text
[사용자 질문]
      ▼
[AI 에이전트 — 계획·검색 여부 결정]     ← Agentic
      ▼
[검색 모듈 A | 검색 모듈 B | 재순위화 모듈] ← Modular
     (하이브리드 검색·필터링·재순위화)   ← Advanced의 품질 개선 기술
      ▼
[에이전트의 근거 평가: 부족하면 재검색]  ← Agentic
      ▼
[LLM 근거 기반 응답]
```

**'개선된 검색 모듈을 에이전트가 자율적으로 선택해 사용한다'**는 것이 가능하다. 단, **모듈은 기능 단위, 에이전트는 목표에 따라 동작을 선택하는 주체**이므로 서로 같은 개념은 아니다. 최종 답변을 작성하는 LLM과 질의 재작성 LLM도 **같은 모델을 다른 프롬프트로 호출**할 수 있다.

### 기술사 답안 문장

> Advanced RAG의 검색 개선 기술을 독립 모듈로 구성하고, AI 에이전트가 상황에 따라 해당 모듈을 선택·반복 호출하여 검색 및 응답 생성을 수행할 수 있다.

# ⅩⅣ. AI 윤리기준 — 2020년과 2026년 구분

## 1. 사람말·기술사 정의

- **AI 윤리:** AI를 개발·활용할 때 **무엇을 지켜야 하는가**에 관한 가치·원칙.
- **기술사 정의:** **AI 개발·활용 과정에서 인간의 존엄성과 권리를 보호하고 사회적 신뢰를 확보하기 위한 가치와 행동원칙.**
- 예: 채용 AI는 지원자를 부당하게 차별하지 않아야 한다.

## 2. 2020년 과기정통부 '인공지능 윤리기준'

최고가치: **인간성(Humanity)**

| 분류 | 기존 노래·두음 | 정확한 명칭 |
|---|---|---|
| **3대 기본원칙** | **인공합** | 인간의 존엄성 · 사회의 공공선 · 기술의 합목적성 |
| **10대 핵심요건 앞 5개** | **인프다침공** | 인권 보장 · 프라이버시 보호 · 다양성 존중 · 침해 금지 · 공공성 |
| **10대 핵심요건 뒤 5개** | **연대책안투** | 연대성 · 데이터 관리 · 책임성 · 안전성 · 투명성 |

**명칭 주의:** 학생의 확정 암기송에서는 **'연대책안투'**라고 부른다. 실제 5요건 가운데 **데이터 관리**가 포함되므로 두음을 문자 그대로 기계적으로 분해하면 혼동할 수 있다. **기존 두음은 변경하지 말고, 정확한 공식 목록을 함께 암기**한다.

# ⅩⅤ. AI 거버넌스 — AI 윤리를 실제로 운영하는 관리체계

## 1. 사람말 원리와 기술사 정의

- **AI 윤리:** “AI가 차별해서는 안 된다”는 **규범·원칙**.
- **AI 거버넌스:** “누가 편향 검사를 하고, 승인하며, 사고가 나면 누가 책임지는가?”를 **조직·프로세스·통제**로 구현.

**기술사 정의:** **AI 전 생애주기의 윤리·법규·위험·성과를 관리하기 위한 원칙·조직·프로세스 기반 관리체계.**

## 2. 구성요소·특징

| 구성요소 | 역할 | 답안 키워드 |
|---|---|---|
| **원칙·정책** | 책임 있는 AI 활용 기준과 위험 수용 기준 수립 | 윤리·법규·가이드라인 |
| **조직·책임** | AI 책임자·위원회·담당자 지정 | 책임소재·R&R |
| **프로세스** | 기획→개발→검증→배포→운영→폐기 통제 | 전 생애주기·승인·변경관리 |
| **기술적 통제** | 편향·설명가능성·보안·성능 검사 | XAI·편향 탐지·모니터링 |
| **감사·증빙** | 점검 결과·의사결정·규제 대응 기록 | 로그·리스크 평가·추적성 |

**주요 특징:** 책임성, 전 생애주기 관리, 위험 기반 통제, 법규 준수, 지속 모니터링.

## 3. 계층형 AI 거버넌스 개념도 — 기존 두음 '기윤사'

```text
 ┌─────────────────────────────────────┐
 │ ③ 사회·법 계층                      │
 │   법률·규제·사회적 책임·공공정책      │
 ├─────────────────────────────────────┤
 │ ② 윤리 계층                         │
 │   윤리원칙·윤리위원회·내부 정책       │
 ├─────────────────────────────────────┤
 │ ① 기술 계층                         │
 │   XAI·편향 탐지·모델 검증·감사 로그   │
 └─────────────────────────────────────┘
```

- 아래쪽 기술적 안전장치 → 조직적 윤리 판단 → 사회·법적 규율을 연계하는 모형.
- 참고 표준: **ISO/IEC 42001** = AI 경영시스템(AIMS) 요구사항. 기술·조직적 관리체계로 AI를 지속 관리.

## 4. AI 윤리 vs AI 거버넌스

| 구분 | AI 윤리 | AI 거버넌스 |
|---|---|---|
| 중심 질문 | **무엇을 지켜야 하나?** | **어떻게 지키도록 관리하나?** |
| 성격 | 가치·원칙 | 관리·통제 체계 |
| 목적 | 인간 존엄·권리·신뢰 보호 | 책임·위험·법규 준수·성과 관리 |
| 구성 | 3대 가치·7대 원칙 등 | 원칙·조직·프로세스·기술·감사 |
| 예 | 채용 AI는 차별해서는 안 된다 | 편향 검사 책임자·절차·감사 기록 운영 |

## 5. IT 거버넌스 vs 데이터 거버넌스 vs AI 거버넌스

| 구분 | IT 거버넌스 | 데이터 거버넌스 | AI 거버넌스 |
|---|---|---|---|
| 관리 대상 | IT 자원·서비스·투자 | 데이터 자산 | AI 모델·시스템·서비스 |
| 핵심 목적 | 경영목표 연계·가치 창출 | 데이터 품질·보호·활용 | 책임 있는 AI 활용·위험 통제 |
| 주요 통제 | 투자·성과·위험·자원 | 품질·메타데이터·접근·계보 | 편향·안전·설명가능성·책임 |
| 대표 책임 | CIO·IT 위원회 | 데이터 소유자·스튜어드 | AI 책임자·AI 거버넌스 위원회 |
| 대표 프레임워크 | COBIT | DAMA-DMBOK | ISO/IEC 42001 |

**관계:** 세 가지는 완전히 별개도, 단순한 직렬 포함 관계도 아니다. 하나의 채용 AI 시스템에 **IT 투자·운영 관리**, **지원자 데이터 품질·권한 관리**, **AI 판단의 편향·책임 관리**가 함께 적용된다.

### 사례 하나로 구분

- IT 거버넌스: 채용 AI 시스템에 예산·인프라를 얼마나 투자할지 결정.
- 데이터 거버넌스: 학습 데이터 품질·권한·삭제 정책 통제.
- AI 거버넌스: 데이터가 정확해도 **모델이 특정 집단을 차별**하는 문제 검사·통제.

# ⅩⅥ. 실제 대화 인출·질문·오답 (첫 번째 파일 작성 이후)

> **채점 원칙:** 실제 대답만 기록. 정답이 질문에 제시되었거나 설명을 본 뒤 따라 말한 경우 독립 인출로 높게 평가하지 않는다. '이해·추론'과 '정의·구성도·표 백지 작성'은 별개의 증거다.

## A. Advanced·Modular·Agentic RAG

| 출제·상황 | 학생 실제 응답·질문 | 판정·교정 |
|---|---|---|
| 재순위화(Re-ranking)의 역할 | `순위라매?` | 이름에 답이 있어 **독립 인출 근거로 보기 어려움** |
| 메타데이터 필터링 해결 사례 | `몰랑` | 당시 미학습; 이후 기술 설명. 이해했다고 완료 처리하지 않음 |
| 기본 vs Advanced RAG 차이 | `검색결과...` | 핵심 방향 **부분 정답**. 정확히는 질의 개선·검색·선별·생성 근거 품질 고도화 |
| 개선 주체는 누구인가? | `대답하는 llm은 아니자나` | 검색기·재순위화 모델·동일/별도 LLM·오케스트레이터 역할을 스스로 질문함 |
| 왜 역할을 나눠서 수행하는가? | `그냥 검색 이래서 처리하면 되지 왜 나누는ㄱ선데?` | 근본 원리 질문. 대규모 1차 후보 검색/정밀 2차 평가의 속도·비용 차이를 설명함 |
| 1차 검색에서 누락한 문서를 재순위화가 복구할 수 있는가? | `아니옹` | **정답**, 후보 외부를 다시 찾지는 못함 |
| 1차 검색에서 중요한 문서를 놓치지 않을 목표 | `재현율` | **정답(독립 인출)**. 이후 정밀도와의 차이 설명함 |
| 자체적으로 재검색 여부 결정하는 형태 | `에이;전특?` | **Agentic RAG 정답**. 발음만 흔들림 |
| Advanced·Modular·Agentic 관계 | `발전된 검색모듈을 에이전트가 자율적으로 쓸수도 있자나?` | **시스템 통합에 대한 정확한 자발적 추론**. 세 구분은 품질·구성·의사결정의 다른 관점 |
| Modular RAG 모듈 교체 이유 | 답하지 않고 다른 질문으로 진행 | **인출 근거 없음** |

## B. AI 윤리·거버넌스

| 출제·상황 | 학생 실제 응답·질문 | 판정·교정 |

| IT·데이터·AI 거버넌스 관계 | 질문하여 설명을 들음 | 비교표 전체 독립 인출/백지 미확인 |

### 인출 수준 종합

- **RAG vs Fine-tuning:** 핵심 차이와 RAG 흐름 일부 구두 인출. 정의·구성도·6행 비교표를 자료 없이 완성한 근거 없음.
- **Advanced·Modular·Agentic RAG:** 원리를 상당히 깊게 질문하고 상호 결합 관계를 자발적으로 추론함. **토픽 전체 구성요소를 암기해 인출하거나 백지로 쓰지는 않음.**
- **2020 AI 윤리:** 3원칙 3/3, 10요건 최초 5/10.
- **2026 AI 윤리:** 3가치 2/3, 7원칙 재인출 5/7.
- **AI 거버넌스:** 책임·원칙·조직·프로세스 이해 및 구두 부분 인출. 3계층·IT/데이터/AI 비교표 독립 인출 미확인.
- **LLM 보안 및 운영 문제:** 오늘 계획의 다음 토픽으로 **아직 본학습 전**.
- **백지 답안:** 오늘 대화에서 작성·제출했다는 증거 없음. 특히 집 과제인 **'RAG와 Fine-tuning 비교표 6줄 + 정의 2개'** 미확인.

# ⅩⅦ. 암기 우선순위 · 다음 복습 · GPT·Claude 인수인계 (갱신)

## 1. 시험 필수 키워드판

| 토픽 | 핵심 암기 내용 |
|---|---|
| Fine-tuning/RAG | 가중치 조정 vs 외부 지식 검색·프롬프트 증강; 6행 비교표 |
| Advanced RAG | **질의 재작성·확장 / 하이브리드 검색 / 메타데이터 필터링 / 재순위화 / 문맥 압축 / 근거 검증** |
| Modular RAG | **라우터 / 검색 모듈 / 결과 결합 / 재순위화 모듈 / 생성 모듈 / 흐름 제어기** |
| Agentic RAG | **계획 / 도구 호출 / 결과 평가 / 재검색 / 반복 제어 / 응답 생성** |
| 3RAG 비교 | **Advanced=품질 / Modular=구성 / Agentic=판단** |
| 2020 윤리 | **인공합 / 인프다침공 / 연대책안투** |
| 2026 윤리 | **존공지 / 인프공책안신투** |
| AI 거버넌스 | **원칙·조직·프로세스·기술·감사 / 기윤사 / ISO/IEC 42001** |
| 기타 노래 | **민혁하안윤 / 목한위거로** — AI 윤리기준 자체가 아니라 공공부문 초거대 AI 도입과 관련 |

## 2. 다음에 한 문제씩 물어볼 것

1. Advanced RAG 기술을 **검색 전·중·후·생성·검증**으로 나누어 설명하라.
2. **Advanced·Modular·Agentic**을 정의·핵심 구성요소·장단점·제어 방식 관점에서 6행 비교하라.
3. Modular RAG에서 **모듈 vs 에이전트**를 구별하고 왜 에이전트 없이도 구현 가능한지 설명하라.
4. **2020년 AI 윤리기준 10대 핵심요건 전체**를 자료 없이 인출하라.
5. **2026년 AI 윤리 7대 원칙 전체**를 자료 없이 인출하라(누락: 공정성·포용성, 신뢰성).
6. **AI 거버넌스 정의·구성요소·계층(기윤사)**를 구두 인출하고, IT/데이터/AI 거버넌스 비교표를 작성하라.
7. 오늘 남은 필수 토픽 **LLM 보안 및 운영 문제**를 진행하라.
8. 집 과제: **RAG vs Fine-tuning 1교시형 백지 1장(정의 2개 + 비교표 6줄)**.

## 3. 다음 AI에게 핵심 인수인계

- 이 MD는 **처음 작성된 455줄 원본의 내용을 유지하고, 이후 학습한 내용을 Ⅹ~ⅩⅦ에 추가한 보충 학습자료**다. 동일 날짜·과목의 원본과 분리된 별도 새 학습일지가 아니다.
- 학생은 **깊은 기술적 의문을 해소하면 잘 이해하지만 한 토픽에 시간이 오래 걸리는 문제**를 스스로 지적했다. 진행은 **깊이 이해 → 정의·구성도·표 → 핵심 인출 → 다음 필수 토픽**으로 빠르게 전환하라.
- **인상적인 자발적 추론:** 'Advanced의 개선된 검색 기술을 Modular 모듈로 만들어 Agentic 에이전트가 필요에 따라 쓰면 되지 않나?'라는 질문으로 3RAG가 비배타적으로 결합 가능함을 정확히 파악했다.
- **효과적인 설명:** RHEL 8/9 버전 오검색, 100만 문서→후보 50→최종 5, 채용 AI 차별 및 책임 소재, 그리고 코끼리 임베딩 비유. 초기 암기송을 활용하되 **새 두음을 임의 변경 금지**.
- **오답 관리:** 2026 윤리 3가치 '인권 보호' 오답 → '인간의 존엄성'. 7원칙에서 **공정성·포용성, 신뢰성** 누락. 2020 10요건 뒤 절반 최초 미인출.
- **기록 상태:** 이 문서는 **교재와 실제 인출 기록의 결합본**이다. 학습한 설명 전체가 학생의 암기 수준을 뜻하지 않는다. 시트 K 수준은 **실제 토픽 전체 인출/백지 증거**에 근거해 판단하라. 오늘 MD 저장과 별개로 토픽 K/N/O·일지 기록은 실제 갱신 여부를 확인해야 한다.
- **남은 오늘 계획:** LLM 보안 및 운영 문제 학습, 저녁 문답, RAG-Fine-tuning 1장 백지. 완료 사실을 추정하지 말 것.
