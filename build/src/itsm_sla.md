# ITSM · SLA (IT 서비스 관리) — 토픽 전체 정리

> 학원 토픽: **클라우드 SLA (최상)** · **ITSM (ISO/IEC 20000) (중)** → 노트는 한 페이지 "ITSM · SLA" 기출: 102 · 118 · 123 · 130 · 133 · 134 · 137 · 139회 + 모의 1주차 (2교시 6번, 1교시 1번 공공 SLA) 이 페이지 하나로 **어떤 방향의 문제가 나와도** 칸을 골라 꺼내 쓰도록 만든 정리. 맨 아래 "문제 유형별 꺼내 쓰기" 참고.

---

## 0. 한눈에 그림

```
ITSM (IT 서비스 관리 = 하는 일)
 ├─ 방법 책: ITIL (모범사례)        ├─ 인증 표준: ISO/IEC 20000
 │
 └─ 그 안의 프로세스: 서비스수준관리 (SLM)
        └─ 관리 대상 약속(계약)
             ├─ SLA : 제공자 ↔ 고객          (손님과의 약속)
             ├─ OLA : 제공자 내부 팀끼리      (주방 ↔ 홀)
             └─ UC  : 제공자 ↔ 외부 공급업체  (식자재 납품 계약)
                  └─ 약속 안의 숫자: SLI (잰 값) → SLO (목표)
```

- 📱 감 잡기: 통신사 약관 "3시간 이상 장애 시 요금 감면" = SLA / 망 감시·복구·원인분석·보상 = ITSM·SLM

## 1. ITSM

**정의**: IT 서비스의 **품질 향상**과 **비즈니스 가치 창출**을 위해, IT를 **고객 중심의 서비스 관점**에서 계획·설계·운영·**지속 개선**하는 관리체계

| 구분    | 내용                                                        |
| ----- | --------------------------------------------------------- |
| 등장 배경 | IT가 비용센터 → 서비스 제공 조직으로 / **아웃소싱·클라우드 확대** → 품질을 정량 관리할 필요 |
| 특징    | 고객 중심 · 프로세스 중심 · 정량적 측정 · 지속적 개선                         |
| 프레임워크 | **ITIL**(모범사례) · **ISO/IEC 20000**(인증 표준) · COBIT(거버넌스)   |

---

## 2. ITIL

**정의**: 효율적인 IT 서비스 관리를 위해 **영국 정부(OGC)**가 개발한 IT 서비스 관리 **모범사례(Best Practice) 프레임워크**

- 버전: **v3 (생명주기 5단계)** → **ITIL 4 (2019)** → **ITIL Version 5 (2026, AI 거버넌스·경험 강조)**
- 현재 소유: PeopleCert
- 답안 본문은 **v3 전·설·전·운·개**로 쓰고, 최신 버전은 가점 한 줄

### 2-1. v3 생명주기 · 🎵 전·설·전·운·개

| 단계                         | 식당 비유     | 주요 프로세스                                                       |
| -------------------------- | --------- | ------------------------------------------------------------- |
| ① 서비스 **전략**               | 무슨 식당 할까  | 서비스 포트폴리오 관리, IT 재무관리, 수요관리                                   |
| ② 서비스 **설계**               | 메뉴·약속 정하기 | **서비스수준관리(SLM)**, 서비스 카탈로그, 가용성, 용량, IT 서비스 연속성, 정보보안, 공급자 관리 |
| ③ 서비스 **전환**               | 새 메뉴 들여오기 | **변경관리**, 릴리즈·배포관리, 서비스 자산·구성관리(**CMDB**), 지식관리               |
| ④ 서비스 **운영**               | 매일 장사     | 이벤트관리, **장애관리**, **문제관리**, 서비스 요청 이행, 접근관리 / 서비스 데스크(기능)      |
| ⑤ **지속적** 서비스 **개선** (CSI) | 계속 더 좋게   | 7단계 개선 프로세스                                                   |

### 2-2. 핵심 프로세스 정의

| 프로세스             | 정의                                             | 키워드                              |
| ---------------- | ---------------------------------------------- | -------------------------------- |
| 서비스 포트폴리오 관리 (①) | 제공할 IT 서비스 전체를 **투자 관점**에서 선정·관리               | 파이프라인 · 카탈로그 · 폐기 서비스            |
| 서비스수준관리 SLM (②)  | 합의된 서비스 수준을 **정의·측정·보고·개선**하여 **SLA를 관리**      | SLA 체결, 정기 리뷰, SIP               |
| 변경관리 (③)         | 변경으로 인한 **위험·서비스 중단을 최소화**하도록 변경을 **평가·승인·통제** | **CAB**, 표준·일반·긴급 변경             |
| 장애관리 (④)         | 서비스 중단 시 **정상 서비스를 최대한 신속하게 복구**               | 신속 복구, 우선순위(영향도×긴급도)             |
| 문제관리 (④)         | 장애 **재발 방지**를 위해 **근본 원인을 분석·제거**              | **RCA**, Known Error, Workaround |
| 7단계 개선 CSI (⑤)   | 서비스·프로세스를 **측정·분석**하여 **지속적으로 개선**             | 측정 → 분석 → 개선, PDCA               |

**장애 vs 문제 vs 변경**: 장애 = **빨리**(일단 살림) → 문제 = **왜**(원인) → 변경 = **고침**(바꿈)

### 2-3. ITIL 4 (가점용, 이름만)

- **SVS**(서비스 가치 시스템) / **4차원**: 조직과 사람 · 정보와 기술 · 파트너와 공급자 · 가치흐름과 프로세스
- **서비스 가치사슬 6활동**: 계획 · 개선 · 참여 · 설계 및 전환 · 획득/구축 · 제공 및 지원
- 프로세스 대신 **34개 프랙티스**

## 3. ISO/IEC 20000

**정의**: 조직이 IT 서비스를 일관되게 제공·개선하도록 **서비스 관리 시스템(SMS)의 요구사항**을 규정한 **ITSM 국제 인증 표준**

- **ITIL vs ISO/IEC 20000**: ITIL = 어떻게 하면 좋은지 **가이드** / ISO 20000 = 인증받으려면 지켜야 할 **요구사항**(감사·인증 가능)
- 구조 (ISO/IEC 20000-1:2018, **PDCA**): 4 조직 상황 · 5 리더십 · 6 기획 · 7 지원 · **8 운영** · 9 성과 평가 · 10 개선

| 8장 운영 그룹               | 주요 활동                                                          |
| ---------------------- | -------------------------------------------------------------- |
| 서비스 포트폴리오              | 서비스 계획, 카탈로그, 자산·구성관리                                          |
| 관계 및 합의                | 고객 관계관리, **서비스수준관리**, 공급자 관리                                   |
| 공급 및 수요                | 예산·회계, 수요관리, 용량관리                                              |
| **설계 · 구축 · 전환** ★133회 | **변경관리** · **서비스 설계 및 전환**(계획 → 설계 → 구축 → 전환) · **릴리즈 및 배포관리** |
| 해결 및 이행                | 장애관리, 서비스 요청관리, 문제관리                                           |
| 서비스 보증                 | 가용성, 서비스 연속성, 정보보안                                             |

## 4. 서비스수준관리 (SLM)

**정의**: 고객과 합의한 서비스 수준을 **정의·협상·측정·보고·개선**하여 서비스 품질을 유지·향상하는 관리 활동

**SLM 프레임워크 구성요소** ★118회

| 구성요소                                 | 뜻                          |
| ------------------------------------ | -------------------------- |
| 서비스 카탈로그                             | 제공하는 서비스 목록·내용             |
| **SLR** (Service Level Requirements) | 고객이 요구하는 서비스 수준 (SLA의 출발점) |
| **SLA**                              | 제공자 ↔ 고객 합의                |
| **OLA**                              | 제공자 내부 부서 간 합의             |
| **UC** (Underpinning Contract)       | 제공자 ↔ 외부 공급업체 계약           |
| 서비스 수준 보고서                           | 월간 측정 결과 보고                |
| **SIP** (Service Improvement Plan)   | 미달 시 개선 계획                 |

---

## 5. SLA

**정의**: IT서비스 제공자와 고객 간 **서비스 품질 수준**을 **합의**하여 관리하기 위한 **공식 계약 문서**

| 구분  | 내용                                                |
| --- | ------------------------------------------------- |
| 필요성 | 품질 **정량화** · **책임 명확화** · 분쟁 예방 · 적정 비용 · 지속 개선   |
| 유형  | 고객 기반 (고객별) · 서비스 기반 (서비스별) · 다수준 (기업 / 고객 / 서비스) |

### 5-1. 구성요소 · 🎵 근·범·지·보

| 구분        | 항목                                          |
| --------- | ------------------------------------------- |
| **근**거자료  | 기본계약서, SLA 협약서                              |
| **범**위    | SoW(작업 범위) · 서비스 카탈로그 · 역할과 책임(R&R)         |
| **지**표·측정 | **SLI · SLO**, 측정 방법·주기, 보고 체계              |
| **보**상    | **Penalty / Incentive**, 서비스 크레딧, 예외(면책) 조항 |

### 5-2. SLA vs OLA vs UC ★123회

| 구분    | SLA          | OLA            | UC                |
| ----- | ------------ | -------------- | ----------------- |
| 당사자   | 제공자 ↔ **고객** | 제공자 **내부 팀끼리** | 제공자 ↔ **외부 공급업체** |
| 식당 비유 | 손님과 약속       | 주방 ↔ 홀 약속      | 식자재 납품 계약         |
| 관계    | 최종 약속        | SLA를 **뒷받침**   | SLA를 **뒷받침**      |

- 💡 OLA·UC 목표가 SLA보다 빡빡해야 SLA를 지킬 수 있음

### 5-3. 수립 절차 ★137회 · 🎵 준·정·협·운·개

| 단계        | 활동                                                           |
| --------- | ------------------------------------------------------------ |
| **준**비    | 대상 서비스 선정, SLR(요구 수준) 파악, 추진 조직 구성                           |
| **정**의    | 서비스 카탈로그, **SLI·SLO 지표와 측정 방법** 정의                           |
| **협**상·체결 | 목표 수준·보상 기준 합의 → SLA 체결                                      |
| **운**영    | 모니터링·측정, **월간 보고**                                           |
| **개**선    | 평가 → 보상(Penalty/Incentive) → **SIP** → 연간 재검토(Annual Review) |

### 5-4. SLI · SLO · SLA

|         | 영어                 | 뜻               | 예                    |
| ------- | ------------------ | --------------- | -------------------- |
| **SLI** | Indicator (계기판 바늘) | 실제로 **잰 값**     | 이번 달 가용률 99.95%      |
| **SLO** | Objective (⭕ 과녁)   | 내부 **목표치**      | 가용률 99.9% 이상         |
| **SLA** | Agreement (🤝 악수)  | 고객과 **계약 + 보상** | 99.5% 미만이면 요금 10% 감액 |

- 흐름: **재고(I) → 목표와 비교(O) → 어기면 보상(A)**
- 💡 **SLO를 SLA보다 빡빡하게** → 계약 위반 전 경고등

### 5-5. 영역별 평가지표와 측정 방법 ★137회

| 영역                 | 지표                                       | 측정 방법                |
| ------------------ | ---------------------------------------- | -------------------- |
| **하드웨어** (서버·스토리지) | 가용률 · CPU/메모리 사용률 · MTBF · MTTR          | SMS(서버 관리 시스템)       |
| **소프트웨어** (응용)     | **응답시간** · 처리량(TPS) · 오류율 · 배치 완료율       | **APM**, 로그          |
| **네트워크**           | 가용률 · 지연(Latency) · **패킷 손실률** · 대역폭 사용률 | **NMS**(네트워크 관리 시스템) |
| **운영·서비스데스크**      | 장애 접수 후 응답시간 · 기한 내 처리율 · 고객 만족도         | ITSM 도구 티켓, 설문       |

- **가용률** = (총 시간 − 중단 시간) ÷ 총 시간 × 100
  - 99.9% ≈ 한 달 약 **43분** 중단 허용 / 99.99% ≈ 1년 약 **52분**
- **MTBF**(고장 사이 평균 시간, 길수록 좋음) / **MTTR**(복구 평균 시간, 짧을수록 좋음)

## 6. SLA 위반 대응과 품질 개선

**정의**: 측정된 SLI가 SLO·SLA에 미달했을 때, **보상과 재발 방지**를 통해 서비스 수준을 회복하는 활동

### 6-1. 위반 대응 · 🎵 탐·통·보·원·개

| 단계        | 활동                                 |
| --------- | ---------------------------------- |
| **탐**지    | 모니터링으로 SLI 측정, 임계치 미달 알람           |
| **통**보    | 고객에게 위반 사실·영향 보고 (월간 SLA 보고서)      |
| **보**상    | **페널티**: 서비스 크레딧(요금 감액), 위약금       |
| **원**인 분석 | **문제관리**로 RCA, 재발 방지 대책 ★          |
| **개**선    | **CSI · SIP** 수립, 필요 시 **SLA 재협상** |

### 6-2. Penalty / Incentive 관리체계 ★123회

- 지표별 측정 → **점수화** → 등급 산정 → 기준 미달 **감액(Penalty)** / 초과 달성 **가산(Incentive)**
- 💡 페널티만 쓰면 제공자가 방어적이 됨 → **인센티브를 같이** 둬야 품질 향상 동기

### 6-3. SIP · Annual Review

- **SIP**: SLA 미달 시 원인 분석을 바탕으로 세우는 **공식 개선 계획** (목표 · 조치 · 일정 · 책임자)
- **Annual Review**: 연 1회 SLA **지표와 목표 수준을 재검토**해 현실에 맞게 조정

## 7. 분야별 SLA

### 7-1. 공공 SLA ★139회 2교시 · 모의 1교시

> 139회: 가. 공공 SLA 개념·도입 필요성 / 나. 정보시스템 등급 분류 기준·등급별 SLA 적용방식 / 다. 표준안 주요 내용(가용률·장애조치 시간·위약금 체계)과 고려사항

**법적 근거** ★쌤: 공공 토픽은 법 조항 필수
- **전자정부법 제56조의3** (정보시스템의 등급) → 등급 분류·관리 의무
- **전자정부법 시행령 제70조의3** (정보시스템의 등급 관리) → 등급산정 기준, 등급별 관리 방안
- 전자정부법 제56조의5 → 주요 정보시스템 장애 시 행안부 통보
- 행안부 「행정·공공기관 정보시스템 서비스수준협약(SLA) 표준안」 (2025.8 확정)
- 행안부 「행정기관 및 공공기관 정보시스템 안전성 고시」 (2026.3 행정예고 → 등급 기준 개편)

- **배경**: 반복되는 행정 전산망 장애 → 디지털행정 서비스 국민 신뢰 제고 대책 → **전자정부법 개정**으로 **정보시스템 등급제 법제화**
- **일정**: 2026년 시범 적용 → **2027년 의무화** (1·2등급 의무, 3·4등급 권고)

**등급 분류 기준** — 기준이 바뀌는 중이라 둘 다 알기
- 처음 기준 (2025 표준안): **업무영향도 40% · 사용자 수 50% · 파급도 10%** → 90점↑ 1등급 / 85↑ 2등급 / 80↑ 3등급 / 미만 4등급 (예외: 국민 안전·생명 위험, 사용자 100만 명↑ → 1등급)
- **새 기준 (2026 안전성 고시안)**: **국민 영향도 70% · 사용자 수 10% · 파급도 10% · 대체 가능성 10%** → **A1~A4** (등급심의위원회 심의)
- 💡 답안: "기존 사용자 수 중심 → **국민 영향도 중심**으로 개편 중" 한 줄이면 최신성 가점

**표준안 주요 내용**

| 구분 | 필수 지표 | 기준 |
|---|---|---|
| 종합서비스 수준 | **정보시스템 가용률** (평가 비중 30%↑) | 1등급 **99.92%** · 2등급 **99.90%** |
| 개별서비스 수준 | **장애조치 최대 허용시간** | 1등급 **2시간** · 2등급 **3시간** |

- 선택 지표 **22개** (장애 건수 · 평균 장애시간 · 변경 절차 준수율 등) → ⚠️ 22개는 **필수가 아니라 선택**
- **위약금**: 종합서비스 수준 미달 시 **월 계약금액 최대 20%** / 장애조치 시간 초과 시 **지체시간(분) 기준 제재금**
- **감면**: 연간 종합평가에서 적정 성과 달성 시 위약금 감면 (⚠️ 가산 보상=인센티브는 없음)
- 신규 차세대 시스템: 구축 후 1년간 **한 등급 낮은 기준** 가능

**적용 시 고려사항 (쟁점)**
- 지체상금과 SLA 위약금 **중복 부과** 논란
- 목표 초과 **인센티브 없음** → 개선 방안으로 **인센티브 도입** 제안
- 유지관리 **예산·인력 현실화**, 클라우드 이용 시 CSP와 **책임 구분** 명확화

### 7-2. 클라우드 SLA ★130 · 134회

- 특징: CSP(클라우드 제공자)와 고객의 **책임 공유** → 어디까지 CSP 책임인지 명시
- 핵심 항목: **가용성**(99.9\~99.99%) · 데이터 백업·복구 · **보안·개인정보** · 데이터 위치 · **서비스 크레딧** · **계약 종료 시 데이터 반환·파기**(출구 전략)
- 공공 SaaS: 공공부문 SaaS 이용 가이드라인 안에 서비스 수준 협약 포함 (위험 관리 · 보안대책과 함께)

### 7-3. 금융 클라우드 SLA ★130회

- 금융 데이터 = 핵심 자산 + 민감정보 → 일반 클라우드 SLA보다 **보안 · 감독 · 연속성** 요건 강화
- 강조 항목: 데이터 보호·암호화 · **감독기관의 검사·접근 권한** · 재해복구(RTO·RPO) · 장애 통보 · 계약 종료 시 데이터 반환·파기
