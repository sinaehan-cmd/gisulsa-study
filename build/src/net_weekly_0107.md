# 기술사 네트워크 학습 정리 — 토픽 ①~⑦

> 작성 기준: 이 대화에서 학습·정리한 내용을 중심으로 정리. **학습 정리 완료 ≠ 최종 인출 통과**.
>
> **원문 보존 안내:** ③ TCP 4-way 및 ④ TCP 3-way는 이 대화에 실제 제시된 답안의 구조·내용을 최대한 보존했다. ① 네트워크 프로토콜과 ② 거리벡터 라우팅은 이전 학습 대화의 확인 가능한 요점에 근거하여 재구성한 부분이므로, 과거 답변의 문장별 완전 일치를 보장하지 않는다.

# ① 네트워크 프로토콜

**학습 상태:** 개념 이해 및 구술 설명 통과 / 정확한 용어와 최종 인출 보완

## Ⅰ. 네트워크 프로토콜의 개요

### 1. 정의

> 네트워크 프로토콜(Network Protocol)이란, 네트워크에서 통신하는 장치 간 데이터 교환을 위해 메시지의 형식·의미·교환 시점 및 절차를 규정한 통신 규약이다.

### 2. 3대 요소

| 요소 | 의미 | 쉬운 설명 |
|---|---|---|
| **구문(Syntax)** | 데이터의 형식, 구조, 인코딩 | 어디에 무엇을 어떤 형식으로 넣는가? |
| **의미(Semantics)** | 메시지 각 필드의 의미와 수행 동작 | 이 값이 무슨 뜻이며 무엇을 해야 하는가? |
| **타이밍(Timing)** | 메시지 전송 시점, 순서, 전송 속도 등의 규칙 | 언제 어떤 순서로, 얼마나 빠르게 주고받는가? |

## Ⅱ. 네트워크 프로토콜의 주요 기능

> 아래 기능은 **네트워크 프로토콜 전반에 나타날 수 있는 기능의 분류**이다. **개별 프로토콜 하나가 모든 기능을 제공한다는 뜻은 아니다.**

### 1. 데이터 전송 관리 측면

| 기능 구분 | 세부 기능 | 내용 |
|---|---|---|
| 데이터 패킷 처리 | 단편화·재조합(Fragmentation/Reassembly) | 전송 단위에 맞게 데이터를 분할하고 수신 측에서 재구성 |
| 데이터 패킷 처리 | 캡슐화(Encapsulation) | 상위 계층 데이터에 제어정보를 추가하여 PDU 형성 |
| 데이터 패킷 처리 | 다중화(Multiplexing) | 여러 통신 흐름을 동일한 통신 자원에 수용 |
| 통신 경로 및 흐름 관리 | 주소 설정(Addressing) | 송수신 대상 식별 |
| 통신 경로 및 흐름 관리 | 순서 제어(Sequencing) | 데이터 순서 식별 및 관리 |
| 통신 경로 및 흐름 관리 | 연결 제어(Connection Control) | 통신 연결의 설정·유지·해제 관리 |

**캡슐화 핵심식:** `SDU + PCI → PDU`

- **SDU(Service Data Unit)**: 상위 계층으로부터 받은 데이터
- **PCI(Protocol Control Information)**: 해당 계층에서 추가하는 제어정보
- **PDU(Protocol Data Unit)**: 해당 계층에서 처리·전달하는 데이터 단위

### 2. 전송 품질 및 보안 관리 측면

| 기능 구분 | 세부 기능 | 내용 |
|---|---|---|
| 데이터 전송 품질 관리 | 흐름 제어(Flow Control) | 수신 처리 능력을 고려한 송신량 조절 |
| 데이터 전송 품질 관리 | 동기화(Synchronization) | 송수신 측 처리 시점·순서 등의 일치 유지 |
| 보안 및 오류 처리 | 오류 제어(Error Control) | 오류·손실 검출 및 복구 처리 |
| 보안 및 오류 처리 | 전송 서비스(Transmission Service) | 프로토콜에 따른 데이터 전달 서비스 제공 |

> **교재 분류 주의:** 위 분류는 학습 당시 사용자가 제시한 교재 목차를 보존한 것이다. '전송 서비스'를 특정 보안 기술과 동일시해서는 안 된다.

## Ⅲ. 구성 및 계층별 예시

```text
응용계층       HTTP 등 — 응용 메시지 형식 및 교환 규칙
전송계층       TCP/UDP — 종단 간 전송 규칙
인터넷/네트워크계층 IP — 논리 주소 및 전달
데이터링크계층   Ethernet — 프레임 형식·로컬 전달
```

- 예시 프로토콜별 제공 기능은 서로 다르다.
- TCP의 연결제어와 오류제어가 같은 TCP 헤더 및 SEQ·ACK 체계를 공유해도 **기능별 목적**은 다르다.

## Ⅳ. 기대효과 및 결론

| 구분 | 기대효과 |
|---|---|
| 상호운용성 | 이기종 장치 간 공통 규칙에 따른 통신 |
| 데이터 전달 | 메시지 형식·주소·순서를 통한 체계적 전달 |
| 전송 안정성 | 프로토콜에 따른 흐름·오류 등 제어 기능 활용 |
| 계층화 | 통신 기능 분리로 구현·운영·확장 용이 |

**마무리 문장:** 네트워크 프로토콜은 구문·의미·타이밍의 통신 규칙을 표준화하여 네트워크 장치 간 상호운용성과 안정적인 데이터 교환을 지원한다.

### 시험 직전 암기

`구문 = 형식 / 의미 = 동작의 뜻 / 타이밍 = 시점·순서·속도`

`전송 관리: 단·캡·다 / 주·순·연`

`품질·보안 관리: 흐·동 / 오·전`

# ② 거리벡터 라우팅(Distance Vector Routing)

**학습 상태:** 정의·특징 이해 및 일부 인출 통과 / 절차·루프 방지 기법 암기 보완

## Ⅰ. 거리벡터 라우팅의 개요

### 1. 정의

> 거리벡터 라우팅이란, 라우터가 인접 라우터와 목적지별 거리 정보를 교환하고, 이를 바탕으로 최적 경로를 계산하여 라우팅 테이블을 갱신하는 동적 라우팅 방식이다.

### 2. 주요 특징

| 특징 | 내용 |
|---|---|
| **분산적(Distributed)** | 중앙 통제 없이 각 라우터가 자신의 테이블 계산 |
| **반복적(Iterative)** | 인접 정보 수신·계산·갱신을 반복 |
| **비동기적(Asynchronous)** | 모든 라우터가 동일 시점에 계산할 필요 없음 |
| 인접 정보 기반 | 전체 토폴로지 대신 이웃의 목적지 거리 정보를 활용 |
| 경로 수렴 | 정보 교환을 거쳐 네트워크 변화가 각 라우터에 반영 |

- **알고리즘:** Bellman-Ford 기반 경로 계산
- **대표 프로토콜:** RIP, IGRP(역사적 사례)
- **주의:** 거리벡터는 라우팅 **방식**, RIP는 해당 방식의 **구체적 프로토콜**이다.

## Ⅱ. 구성도 및 동작 원리

```text
    [목적지 네트워크 D]
           ↑
    R3 ── 비용 2 ── R2 ── 비용 1 ── R1
                        ↑               │
                        └── 거리정보 ────┘

R1이 R2로부터 'R2→D 거리 = 2'를 받으면
R1이 계산한 R2 경유 D까지의 비용 = 1 + 2 = 3
→ 기존 후보 경로와 비교 후 라우팅 테이블 갱신
```

> 위 비용값은 계산 원리를 설명하기 위한 예시이다. RIP는 비용 척도로 홉 수를 사용한다.

### 1. 동작 절차

| 단계 | 동작 | 내용 |
|---|---|---|
| ① | 인접 정보 수신 | 이웃 라우터의 목적지별 거리 정보 수신 |
| ② | 경로 비용 계산 | 인접 라우터까지 비용 + 이웃이 알려준 목적지 거리 |
| ③ | 후보 경로 비교 | 기존 경로와 새 후보 경로의 비용·다음 홉 비교 |
| ④ | 테이블 갱신 | 선택된 경로의 비용과 Next Hop 반영 |
| ⑤ | 반복·전파 | 변화된 정보의 교환으로 라우팅 정보 수렴 |

**경로 계산과 패킷 전달은 다르다.** 계산으로 라우팅 테이블에 `목적지→다음 홉`을 기록한 뒤, 실제 패킷은 그 Next Hop을 향해 전달한다.

## Ⅲ. 구성요소 및 대표 프로토콜

| 구성요소 | 역할 |
|---|---|
| 라우터 | 분산된 위치에서 자체 경로 계산 |
| 인접 라우터 | 거리 정보 교환 상대 |
| 거리 벡터 | 목적지별 경로 비용 정보 |
| 메트릭(Metric) | 경로 비교 기준(예: 홉 수) |
| 라우팅 테이블 | 목적지·비용·다음 홉 저장 |
| Bellman-Ford | 인접 거리 정보로 경로 비용 계산 |

| 프로토콜 | 핵심 특징 |
|---|---|
| RIP | 홉 수 기반 거리벡터. **15홉까지 도달 가능, 16홉은 도달 불가능** |
| IGRP | 복합 메트릭을 활용한 Cisco의 역사적 거리벡터 프로토콜 |
| OSPF | 비교용 **링크상태(Link State)** 라우팅 프로토콜. 거리벡터에 속하지 않음 |

## Ⅳ. 라우팅 루프 문제 및 방지 기법

### 1. 문제

라우터들이 오래되거나 불일치한 경로 정보를 서로 알려주면, 도달할 수 없는 목적지를 향해 패킷이 라우터 사이를 순환할 수 있다. 거리 정보가 점진적으로 증가하는 **Count-to-Infinity** 문제와 연결된다.

### 2. 방지 기법

| 기법 | 핵심 동작 | 기억 포인트 |
|---|---|---|
| Maximum Hop Count | 최대 홉 수를 제한하여 무한 거리 증가 억제 | RIP: 16은 무한대 |
| Hold Down Timer | 경로 장애 후 일정 기간 불안정한 업데이트 채택 제한 | 불안정 경로의 즉각 재채택 억제 |
| Split Horizon | 특정 이웃에게서 학습한 경로를 **그 이웃에게 다시 광고하지 않음** | 되돌려 알려주지 않음 |
| Route Poisoning | 장애 경로를 **무한대 메트릭으로 광고** | 끊긴 경로를 무효라고 전파 |
| Poison Reverse | 이웃에게서 학습한 경로를 **그 이웃에게 무한대 메트릭으로 광고** | 거꾸로 알리되 무한대 |

### 3. 특히 헷갈리는 기법 비교

| 비교 | 차이 |
|---|---|
| Split Horizon vs Poison Reverse | 전자는 해당 이웃에게 광고 **생략**, 후자는 그 이웃에게 **무한대 값으로 광고** |
| Route Poisoning vs Poison Reverse | 전자는 **장애 발생 경로를 무효로 전파**, 후자는 **학습해 온 이웃 방향에 역광고하면서 무한대로 표시** |

> 장애에 대한 루프 억제 기법은 개별 프로토콜의 실제 동작 방식과 구현에 따라 적용된다. 위 표는 기술사 시험 학습을 위한 기본 개념 구분이다.

## Ⅴ. 기대효과 및 고려사항

| 구분 | 내용 |
|---|---|
| 분산 경로 관리 | 각 라우터가 인접 정보로 경로 계산 |
| 자동 경로 갱신 | 라우팅 정보 변화에 따른 경로 조정 |
| 구성·운영 단순성 | 특히 RIP 등 단순 구현에서 작은 네트워크 운영 용이 |
| 한계 | 수렴 지연, 라우팅 루프 및 Count-to-Infinity 위험 |
| 대응 | 홉 제한·홀드다운·수평분할·포이즈닝 적용 |

**마무리 문장:** 거리벡터 라우팅은 인접 라우터의 거리 정보를 반복 교환하여 분산적으로 경로를 갱신하되, 수렴 지연 및 라우팅 루프 문제를 방지하기 위한 보완 기법이 필요하다.

### 시험 직전 암기

`특징: 분산·반복·비동기`

`절차: 수신 → 계산 → 비교 → 갱신 → 전파`

`루프 방지: 최대 홉·홀드다운·수평분할·라우트 포이즈닝·포이즌 리버스`

**연계 학습(미완료):** RIP vs OSPF, IGP vs EGP

# ③ TCP 4-way Handshake — 연결 해제

**학습 상태:** 원리 이해 통과 / LAST_ACK 명칭 인출 보완

## Ⅰ. TCP 4-way Handshake의 개요

### 1. 정의

> TCP 4-way Handshake란, 연결된 양 끝단에서 FIN과 ACK를 교환하여 미전송 데이터의 손실을 방지하고, TCP 연결을 정상적으로 해제하는 연결 종료 절차이다.

### 2. 목적 및 특징

| 구분 | 주요 내용 |
|---|---|
| 연결 종료 | TCP 연결의 양방향 전송을 순차적으로 종료 |
| 독립적 종료 | 양쪽이 자신의 송신 방향을 개별적으로 종료 |
| 데이터 보호 | 남은 데이터 전송 후 연결 종료 가능 |
| 신뢰성 확보 | FIN 재전송 및 ACK 확인을 통한 종료 처리 |
| 지연 패킷 대응 | TIME_WAIT을 통해 이전 연결의 지연 패킷 영향 방지 |

## Ⅱ. TCP 4-way Handshake 구성 및 동작

### 1. 구성도

```text
         Client(먼저 종료)                   Server(나중 종료)
           ESTABLISHED                        ESTABLISHED
                |                                   |
                | --------- ① FIN --------------> |
          FIN_WAIT_1                                |
                | <-------- ② ACK ---------------- |  CLOSE_WAIT
          FIN_WAIT_2                         (잔여 데이터 처리)
                |                                   |
                | <-------- ③ FIN ---------------- |  LAST_ACK
                | --------- ④ ACK --------------> |
           TIME_WAIT                              CLOSED
                |
           2MSL 대기
                |
              CLOSED
```

**도식에서 화살표의 FIN·ACK는 행위(메시지), FIN_WAIT·CLOSE_WAIT·LAST_ACK·TIME_WAIT는 상태다.**

### 2. 동작 절차 — 행위와 상태 구분

| 단계 | 송수신 행위(Action) | 상태 전이(State) 및 의미 |
|---|---|---|
| ① 종료 요청 | Client → Server: **FIN** | Client: `FIN_WAIT_1` |
| ② 요청 확인 | Server → Client: **ACK** | Server: `CLOSE_WAIT`; Client가 ACK 수신하면 `FIN_WAIT_2` |
| ③ 종료 통보 | Server → Client: **FIN** | Server: `LAST_ACK` |
| ④ 종료 확인 | Client → Server: **ACK** | Client: `TIME_WAIT`; Server가 ACK 수신하면 `CLOSED` |
| ⑤ 종료 완료 | TIME_WAIT 타이머 만료 | Client: `CLOSED` |

> 실제 TCP는 ACK와 FIN이 함께 전달되거나 양쪽에서 동시에 종료하는 형태도 가능하다. 위 그림은 **기본적인 순차 종료 사례**다.

## Ⅲ. TCP 연결 종료의 주요 상태

| 상태 | 발생 시점 | 핵심 역할 |
|---|---|---|
| `ESTABLISHED` | 연결 설정 완료 | 양방향 데이터 송수신 |
| `FIN_WAIT_1` | 먼저 FIN 송신 | 자신의 FIN에 대한 ACK 대기 |
| `FIN_WAIT_2` | 자신의 FIN에 대한 ACK 수신 | 상대방 FIN 대기 |
| `CLOSE_WAIT` | 상대 FIN 수신 후 ACK 송신 | 자신의 송신 방향 종료 준비 |
| `LAST_ACK` | 나중에 자신의 FIN 송신 | 마지막 ACK 수신 대기 |
| `TIME_WAIT` | 마지막 ACK 송신 | 재전송 FIN 대응 및 지연 패킷 소멸 대기 |
| `CLOSED` | 종료 절차 완료 | 연결 해제 |

### FIN_WAIT_1과 LAST_ACK 구분

| 비교 | FIN_WAIT_1 | LAST_ACK |
|---|---|---|
| 종료 주체 | 먼저 종료 요청한 쪽 | 상대 요청 후 종료하는 쪽 |
| 직전 행위 | 최초 FIN 송신 | 자신의 FIN 송신 |
| 대기 대상 | 자신의 FIN에 대한 ACK | 마지막 ACK |
| 다음 상태 | 일반적으로 FIN_WAIT_2 | CLOSED |

## Ⅳ. TIME_WAIT의 필요성

### 1. 마지막 ACK 유실 대응

마지막 ACK가 유실되면 상대방은 FIN을 재전송할 수 있다. TIME_WAIT 상태에서는 재전송된 FIN에 다시 ACK로 응답할 수 있다.

### 2. 지연 패킷 영향 방지

기존 연결에서 지연된 패킷이 이후 동일한 연결 식별정보를 사용하는 통신에 영향을 주지 않도록 일정 시간 대기한다.

### 3. 2MSL 개념

- **MSL(Maximum Segment Lifetime)**: 네트워크에서 세그먼트가 유효하게 존재할 수 있는 최대 시간
- **2MSL**: 일반적인 TCP 설명에서 TIME_WAIT을 유지하는 시간
- 실제 대기 시간은 운영체제 구현에 따라 달라질 수 있다.

## Ⅴ. 기대효과 및 결론

| 구분 | 기대효과 |
|---|---|
| 안전한 연결 종료 | 각 방향의 데이터 전송 종료를 독립적으로 관리 |
| 데이터 신뢰성 | 남은 전송 데이터 처리 및 종료 확인 |
| 통신 안정성 | FIN 재전송과 TIME_WAIT을 통한 종료 처리 |
| 연결 관리 | 상태 전이에 따른 체계적인 자원 정리 |

**기술사 답안 마무리 문장:**

> TCP 4-way Handshake는 FIN·ACK 기반의 단계적 연결 종료와 TIME_WAIT을 통해 데이터 전송의 신뢰성 및 안전한 연결 해제를 보장한다.

### 시험 직전 암기

**행위:** `FIN → ACK → FIN → ACK`

**먼저 종료:** `FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED`

**나중 종료:** `CLOSE_WAIT → LAST_ACK → CLOSED`

**TIME_WAIT 2대 목적:** 마지막 ACK 유실 대응 + 지연 패킷 소멸

# ④ TCP 3-way Handshake — 연결 설정

**학습 상태:** 정리 완료 / 순서번호·ACK 원리 이해 보완 / 최종 인출 미통과

## Ⅰ. TCP 3-way Handshake의 개요

### 1. 정의

> TCP 3-way Handshake란, 송수신 단말 간 SYN·ACK 제어 메시지를 3단계로 교환하여 초기 순서번호(ISN)를 동기화하고 신뢰성 있는 TCP 연결을 설정하는 절차이다.

### 2. 주요 특징 및 목적

| 구분 | 주요 내용 |
|---|---|
| 연결지향성 | 데이터 전송 전 논리적 연결 설정 |
| 양방향 확인 | 송수신 양측의 연결 요청 및 응답 확인 |
| 순서번호 동기화 | 양측 초기 순서번호(ISN) 교환·확인 |
| 상태 관리 | CLOSED·LISTEN에서 ESTABLISHED까지 상태 전이 |
| 연결 준비 | 데이터 전송에 필요한 TCP 연결 상태 및 제어정보 협상 |

## Ⅱ. TCP 3-way Handshake의 구성 및 동작

### 1. 구성도

```text
           Client                              Server
           CLOSED                              LISTEN
              |                                  |
              | ----- ① SYN, SEQ=x ----------> |
           SYN_SENT                              |
              | <--- ② SYN+ACK, SEQ=y, ACK=x+1 | SYN_RECEIVED
              |                                  |
              | ----- ③ ACK, ACK=y+1 --------> |
        ESTABLISHED                         ESTABLISHED
              | <-------- 데이터 송수신 --------> |
```

> 클라이언트가 능동적으로 연결을 시작하고, 서버가 수동적으로 수락하는 일반적인 사례이다.

### 2. 동작 절차 — 행위와 상태 구분

| 단계 | 행위(Action) | 상태(State) |
|---|---|---|
| ① 연결 요청 | Client → Server: **SYN, SEQ=x** | Client: `SYN_SENT` |
| ② 요청 수락·응답 | Server → Client: **SYN, SEQ=y + ACK=x+1** | Server: `SYN_RECEIVED` |
| ③ 연결 확인 | Client → Server: **ACK=y+1** | Client: `ESTABLISHED`; Server는 ACK 수신 시 `ESTABLISHED` |

**핵심:** SYN은 순서번호 공간을 1 소비하므로 상대 SYN에 대한 ACK 번호는 상대 ISN+1이다.

### 3. 주요 상태

| 상태 | 의미 |
|---|---|
| `CLOSED` | 연결되지 않은 초기 상태 |
| `LISTEN` | 서버가 연결 요청 대기 |
| `SYN_SENT` | 클라이언트가 SYN 송신 후 응답 대기 |
| `SYN_RECEIVED` | 서버가 SYN+ACK 송신 후 마지막 ACK 대기 |
| `ESTABLISHED` | 연결 설정 완료, 데이터 송수신 가능 |

## Ⅲ. TCP 3-way Handshake의 구성요소 — 보충 상세

| 구성요소 | 기술적 기능 | 3-way에서의 역할 |
|---|---|---|
| **SYN Flag** | 순서번호 동기화 | 최초 연결 요청, ISN 전달 |
| **ACK Flag** | 확인응답 필드 유효 표시 | 상대 SYN 수신 확인 |
| **ISN** | 연결 시작 시 초기 순서번호 | 양쪽이 독립적으로 선택한 시작 번호 교환 |
| **Sequence Number** | 바이트 단위 전송 순서 관리 | 자신의 ISN 표시 |
| **Acknowledgment Number** | 다음 수신 기대 번호 표시 | 상대 ISN+1 전달 |
| **TCP 연결 상태** | 연결 진행 단계 관리 | SYN_SENT → ESTABLISHED 등 상태 전이 |

### 1. SYN — 연결 시작 요청

클라이언트가 서버에 연결 요청을 보내면서 자신의 시작 순서번호를 알려준다. 서버도 응답할 때 SYN으로 자기 시작 번호를 알려준다.

### 2. ACK — 상대방의 순서번호 확인

서버는 클라이언트 SYN을 확인하고, 클라이언트는 서버 SYN을 확인한다. **ACK 플래그**는 확인응답번호 필드가 유효하다는 표시이며 **ACK 번호**는 다음에 받기를 기대하는 순서번호이다.

### 3. ISN — 새로운 연결의 출발점

TCP에서는 연결의 각 방향마다 초기 순서번호를 선택하며, 이를 바탕으로 이후 전송되는 데이터의 순서·수신 위치를 추적한다.

### 4. SEQ / ACK 번호 — 전송의 기준

연결 설정 이후 TCP는 SEQ로 바이트 순서를 식별하고 ACK로 연속 수신된 범위를 확인한다. 이 정보를 바탕으로 손실 감지, 중복 데이터 구분, 재전송 등이 이루어진다.

### 5. TCP 상태 — 연결 진행 상황

`SYN_RECEIVED`는 최종 ACK를 기다리는 상태이고, `ESTABLISHED`는 연결 설정이 완료된 상태이다.

## Ⅳ. 순서번호·ACK 번호의 원리 — 보충 설명

### 1. SEQ와 ACK 번호 구분

| 구분 | Sequence Number (SEQ) | Acknowledgment Number (ACK 번호) |
|---|---|---|
| 의미 | 내가 보내는 데이터의 순서 위치 | 상대방에게 다음으로 받기 원하는 순서 위치 |
| 기준 | 내 송신 방향 | 상대방 송신 방향 |
| 목적 | 데이터 순서 관리·재전송 | 누적 수신 확인 |
| 3-way에서 | 자신의 초기 순서번호(ISN) 제시 | 상대 ISN 수신 확인 |

**ACK 플래그 ≠ ACK 번호**: ACK 플래그는 유효성 표시, ACK 번호는 실제 다음 기대 순서번호 값.

### 2. 왜 x+1, y+1인가?

클라이언트 초기 순서번호를 100, 서버 초기 순서번호를 500으로 가정한다.

| 단계 | 메시지 | SEQ | ACK 번호 | 뜻 |
|---|---|---:|---:|---|
| ① Client → Server | SYN | 100 | — | 내 시작 번호는 100 |
| ② Server → Client | SYN+ACK | 500 | 101 | 네 SYN 확인, 내 시작 번호는 500 |
| ③ Client → Server | ACK | 101 | 501 | 네 SYN 확인 |

**SYN은 데이터가 없어도 순서번호 공간을 1 소비하기 때문에** 확인응답번호가 `ISN+1`이다. **FIN도 1 소비**한다. 반면 **순수 ACK는 순서번호 공간을 소비하지 않는다.**

### 3. 데이터 전송에서는 왜 +1이 아닌가?

3-way 완료 후 클라이언트가 데이터를 전송한다고 가정한다.

| 전송 | 송신 SEQ | 데이터 크기 | 수신 측 ACK 번호 |
|---|---:|---:|---:|
| 첫 데이터 | 101 | 100바이트 | 201 |
| 두 번째 데이터 | 201 | 50바이트 | 251 |
| 세 번째 데이터 | 251 | 200바이트 | 451 |

**TCP 순서번호는 패킷 개수가 아니라 바이트 위치를 기준으로 관리한다.** 따라서 연속된 100바이트를 수신하면 ACK는 1이 아닌 100 증가한다.

### 4. 데이터가 중간에서 손실되면?

- `SEQ=101`, 100바이트 정상 수신 → 수신 측 `ACK=201`
- `SEQ=201`, 100바이트 **손실**
- `SEQ=301`, 100바이트 도착 → 중간 201~300 바이트가 비어 있으므로 **누적 ACK는 여전히 201**

TCP는 연결 설정 때와 데이터 전송·오류제어 때 **같은 SEQ/ACK 번호 체계**를 사용한다. 다만 연결 설정 시에는 SYN의 순서번호 공간 1 소비를, 데이터 전송에서는 수신한 연속 바이트 범위를 확인한다.

> **핵심 요약:** `SYN·FIN = 각각 +1 / 데이터 = 바이트 수만큼 / 순수 ACK = 순서번호 소비 없음`

### 5. 한 줄로 연결한 예시

```text
Client → Server : SYN, SEQ=100
Server → Client : SYN+ACK, SEQ=500, ACK=101
Client → Server : ACK, SEQ=101, ACK=501

연결 설정 후
Client → Server : 데이터 10바이트, SEQ=101
Server → Client : ACK=111
```

**같은 TCP ACK이지만, ACK 번호가 '항상 1씩' 증가하는 것은 아니다.** 수신 측이 다음에 연속해서 받고 싶은 바이트의 번호를 알려주는 것이다.

> **학습 상태 주의:** 이 SEQ·ACK 원리는 아직 사용자의 이해·인출 확인이 끝나지 않았다. 이 노트의 예시는 암기 완료의 증거가 아니다.

## Ⅴ. TCP 3-way Handshake의 기대효과

| 구분 | 동작 근거 | 기대효과 |
|---|---|---|
| 양방향 연결 확인 | SYN·SYN+ACK·ACK 교환 | 양측의 연결 의사 및 응답 확인 |
| 순서번호 동기화 | 양측 ISN 교환 및 확인 | 송수신 데이터의 순서 관리 기반 |
| 중복 연결 요청 대응 | 3단계 확인 절차 | 오래된 SYN으로 인한 잘못된 연결 설정 위험 감소 |
| 신뢰성 있는 전송 준비 | SEQ·ACK 기준 확립 | 손실·중복 감지 및 재전송 기능의 기반 |
| 전송 조건 협상 | SYN 세그먼트의 TCP 옵션 교환 | MSS·Window Scale 등 통신 조건 설정 |
| 연결 상태 관리 | TCP 상태 전이 | 연결 수립 단계의 체계적 관리 |

**주의:** 3-way 자체가 전송 중의 모든 데이터 손실을 방지하는 것이 아니다. **연결과 초기 번호를 확립해 이후 TCP의 신뢰성 기능이 작동할 기반**을 제공한다.

### 기술사 1교시 압축용 구성요소

| 구분 | 주요 내용 |
|---|---|
| 연결 제어 | SYN: 연결 요청 및 ISN 동기화 |
| 수신 확인 | ACK: 확인응답번호 유효 표시 |
| 순서 관리 | SEQ: 송신 바이트 순서번호 |
| 수신 관리 | ACK Number: 다음 수신 기대번호 |
| 초기 동기화 | ISN: 양단 초기 순서번호 |
| 상태 관리 | SYN_SENT, SYN_RECEIVED, ESTABLISHED |

**기술사 답안 마무리 문장:**

> TCP 3-way Handshake는 SYN·ACK 교환을 통해 양단의 초기 순서번호를 동기화하고 연결 상태를 확립함으로써 신뢰성 있는 데이터 전송의 기반을 제공한다.

### 시험 직전 암기

**정의:** SYN·ACK 3단계 교환을 통한 ISN 동기화 및 TCP 연결 설정 절차

**행위:** `SYN → SYN+ACK → ACK`

**클라이언트 상태:** `CLOSED → SYN_SENT → ESTABLISHED`

**서버 상태:** `LISTEN → SYN_RECEIVED → ESTABLISHED`

**순서번호:** `Client ISN=x / Server ISN=y / SYN+ACK의 ACK=x+1 / 마지막 ACK=y+1`

# ⑤ TCP 혼잡제어(TCP Congestion Control)

**학습 상태(2026-10-27):** Slow Start·Congestion Avoidance·Fast Retransmit·Fast Recovery 핵심 원리 인출 통과 / 주요 알고리즘 비교 및 종합 답안 독립 재현 보완.

## Ⅰ. 개요

### 1. 정의

> **TCP 혼잡제어란 네트워크의 혼잡 상태를 추정하고 혼잡 윈도우(CWND)를 동적으로 조절하여 전송량을 제어함으로써 패킷 손실과 혼잡 붕괴를 방지하고 전송 효율을 높이는 기법이다.**

### 2. 혼잡제어가 필요한 이유

- 송신자가 네트워크 처리 능력을 초과해 데이터를 보내면 라우터 큐 증가·지연·패킷 손실·재전송 폭증이 발생할 수 있다.
- **흐름제어(RWND)는 수신자의 처리 여유**, **혼잡제어(CWND)는 네트워크의 수용 여유**를 고려한다. 둘은 목적이 다르다.
- TCP의 실제 전송 가능 미확인 바이트량은 대체로 `min(CWND, RWND)`에 제한된다. 새로 보낼 수 있는 바이트량은 이미 전송했으나 확인받지 않은 데이터량도 고려한다.

### 3. 특징

| 구분 | 특징 | 설명 |
|---|---|---|
| 제어 대상 | 송신 측 전송량 | 송신 TCP가 CWND를 조절 |
| 제어 기준 | 네트워크 혼잡 징후 | 손실, RTT 증가, ECN 등 알고리즘별 신호 활용 |
| 동적 적응 | AIMD 등 | 이용 가능 용량을 탐색하고 혼잡 시 감속 |
| 효율성 | 자원 활용도 향상 | 혼잡 붕괴 방지 및 안정적 전송 지원 |
| 종단 간 처리 | TCP 송신자의 제어 | 양쪽 TCP가 반드시 같은 혼잡제어 알고리즘일 필요는 없음 |
| TCP 윈도우 연계 | CWND·RWND 공동 제약 | 혼잡제어와 흐름제어를 함께 준수 |

## Ⅱ. 동작 개념 구성도

```text
       ┌───────────────────────────────────────┐
       │ 송신 TCP: 혼잡제어 알고리즘            │
       │  CWND / ssthresh / RTT / RTO          │
       └─────────────────┬─────────────────────┘
                         │ 전송량 제한
                         ▼
                [송신 윈도우]
              min(CWND, RWND)
                         │ TCP 세그먼트
                         ▼
          [네트워크: 라우터·큐·링크]
                         │
                         ▼
                    [수신 TCP]
                         │ ACK / 혼잡 신호
                         └──────────────────────► 송신 TCP

  정상 ACK 수신 → CWND 증가    손실·혼잡 감지 → CWND 감소
```

> **구성도 주의:** ACK로 손실을 추정하는 것은 전통적인 손실 기반 TCP 설명이다. 현대 TCP는 알고리즘에 따라 지연·ECN·대역폭 추정 등도 활용한다.

## Ⅲ. 주요 용어 및 구성요소

| 구분 | 구성요소 | 정확한 역할 |
|---|---|---|
| 혼잡량 | **CWND(Congestion Window)** | 송신 측이 혼잡 상태를 고려해 설정하는 미확인 데이터량 한도(바이트 기준) |
| 수신량 | **RWND(Receive Window)** | 수신 측이 버퍼 여유에 따라 광고하는 수신 가능량 |
| 임계값 | **ssthresh(Slow Start Threshold)** | Slow Start와 Congestion Avoidance 증가 방식을 구분하는 기준 |
| 시간 | **RTT(Round Trip Time)** | 데이터 전송과 그 확인응답에 소요되는 왕복시간 |
| 시간 | **RTO(Retransmission Timeout)** | 재전송 타이머의 만료 기준시간 |
| 세그먼트 | **MSS(Maximum Segment Size)** | TCP 세그먼트 하나에 실을 수 있는 최대 TCP 데이터 크기(헤더 제외) |
| 확인 | **ACK / 중복 ACK** | 수신 확인 및 일부 손실 추정에 사용 |
| 손실 복구 | **Fast Retransmit** | 전형적 TCP에서 중복 ACK 3개를 손실 징후로 보고 RTO 만료 전 재전송 |

### MSS와 CWND는 왜 둘 다 필요한가?

- **MSS는 세그먼트 하나의 최대 데이터 크기**이다. 경로 MTU와 헤더 공간을 고려해 한 세그먼트에 얼마나 담을 수 있는지 제약한다.
- **CWND는 네트워크에 미확인 상태로 떠 있어도 되는 데이터의 총량**이다. 세그먼트의 개수가 아니라 바이트 단위로 제약한다.
- 예: `MSS=1,000B`, `CWND=5,000B`이면 다른 제약과 기존 미확인 데이터가 없을 때 **1,000B짜리 세그먼트 약 5개분**을 연속 송신 가능하다. 작은 세그먼트라면 세그먼트 개수는 달라질 수 있다.
- `CWND=8 MSS`는 **MSS 크기 8개분의 바이트량**이라는 표현이며 반드시 정확히 8개의 세그먼트를 보내라는 명령이 아니다.
- 별개로 **TCP SEQ는 세그먼트 헤더에 실리지만 세그먼트 일련번호가 아닌 바이트 스트림의 시작 번호**이다.

## Ⅳ. 네 가지 기본 동작

| 구분 | 기법 | 조건 및 동작 | CWND 변화 |
|---|---|---|---|
| 증가 | **Slow Start** | 연결 시작·심각한 손실 후 전송 여유 탐색 | ACK에 따라 증가, 대략 RTT마다 배증(지수 증가) |
| 증가 | **Congestion Avoidance** | ssthresh 부근/이후 완만한 탐색 | 전통적 AIMD에서 대략 RTT마다 1 MSS씩 선형 증가 |
| 손실 감지·복구 | **Fast Retransmit** | 3개의 중복 ACK를 받으면 빠진 세그먼트를 RTO 전 재전송 | 즉시 손실 대응 시작 |
| 손실 후 복구 | **Fast Recovery** | Reno 계열에서 3중복 ACK 손실 후 Slow Start로 바로 돌아가지 않고 전송 지속 | ssthresh 조정, CWND 감소·복구 |

**암기:** `슬로 스타트(지수) → 혼잡 회피(선형) → 빠른 재전송(3중복 ACK) → 빠른 회복(감속 후 유지)`.

### 1. Slow Start와 혼잡 회피의 차이

```text
CWND (MSS 단위의 개념적 예시)
 16 |                 ●──●──●──●  혼잡 회피: 완만한 증가
  8 |           ●
  4 |       ●
  2 |    ●
  1 | ●
    +--------------------------------------> 시간(RTT)
      초기 지수 증가 → ssthresh 이후 선형 증가
```

- 교과서의 `1 → 2 → 4 → 8 MSS`는 **동작 원리를 나타내는 예시**다. 모든 TCP 연결의 현대적 초기 CWND가 1 MSS라는 뜻은 아니다.
- 그래프에 표시된 `ssthresh1·ssthresh2·ssthresh3`는 서로 독립적인 임계값 세 개가 아니라 **혼잡 사건에 따라 변경된 같은 변수의 시점별 값**이다.

### 2. Timeout과 3중복 ACK 구별

| 구분 | RTO Timeout | 3 Dup ACK |
|---|---|---|
| 상황 | 기대한 ACK가 제때 오지 않음 | 뒤쪽 세그먼트는 도착하나 중간 데이터가 비어 동일 ACK 반복 |
| 일반적 판단 | 더 심각하거나 불확실한 손실 징후 | 일부 경로가 계속 작동하는 손실 징후 |
| 고전 Reno 대응 | ssthresh 감소, CWND를 작은 값으로 재설정 후 Slow Start | Fast Retransmit + Fast Recovery |
| 시험 키워드 | **타임아웃 → Slow Start 재진입** | **3중복 ACK → 빠른 재전송·회복** |

> 고전 Reno 설명에서 `ssthresh ≈ 손실 당시 flight size/2`, RTO 후 `cwnd=1 MSS` 등은 **교재용 고전 모델**이다. 실제 현대 구현에는 초기 윈도우·복구·손실 처리 차이가 있다.

### 3. Reno Fast Recovery 핵심

- 이미 후속 세그먼트가 수신되고 있으므로 전체 연결이 완전히 멈췄다고 단정하지 않는다.
- 빠진 세그먼트를 재전송하고 혼잡 윈도우를 낮춘 뒤 확인응답 흐름을 이용해 회복한다.
- Timeout처럼 매번 초기 Slow Start로 돌아가는 비용을 줄이는 것이 핵심이다.

## Ⅴ. 혼잡제어 알고리즘 비교

| 구분 | 알고리즘 | 핵심 기술·차이점 |
|---|---|---|
| 손실 기반·전통 | **Tahoe** | Slow Start·Congestion Avoidance·Fast Retransmit, 손실 후 Slow Start로 복귀; Reno의 Fast Recovery 없음 |
| 손실 기반·전통 | **Reno** | Tahoe에 Fast Recovery 추가; 3중복 ACK 손실에 빠른 회복 |
| 손실 기반·전통 | **NewReno** | Partial ACK를 이용해 한 윈도우 안의 복수 손실 복구 개선 |
| 손실 기반·고속망 | **BIC** | 이진 탐색 기반 윈도우 증가로 고속·고지연 환경 대응 |
| 손실 기반·고속망 | **CUBIC** | 3차 함수 기반으로 시간에 따라 CWND 증가를 조절 |
| 손실 기반·고속망 | **H-TCP** | 마지막 혼잡 사건 이후 시간 등으로 증가율 조절 |
| 지연 기반 | **Vegas** | RTT 기반 기대·실제 전송률 차이로 혼잡 조기 추정 |
| 지연 기반 | **FAST TCP** | RTT 지연 정보와 제어 모델을 이용한 윈도우 조절 |
| 대역폭 추정 계열 | **Westwood / Westwood+** | ACK를 바탕으로 이용 가능 대역폭을 추정하여 손실 후 전송량 조절; **순수 지연 기반이라고만 분류하기는 부정확** |

> **교재 주의:** 학습 교재가 Westwood를 지연 기반 그룹에 배치했다면 교재 분류는 기억하되, 기술적 설명은 **ACK 기반 대역폭 추정**으로 쓰는 편이 정확하다.

### Reno는 모든 TCP의 고정 동작인가?

- **아니다.** TCP 헤더·SEQ·ACK 등 통신 규칙과 송신자 내부의 혼잡제어 알고리즘은 구별된다.
- 송신 측 OS/네트워크 스택은 서로 다른 알고리즘을 사용할 수 있고 상대방이 꼭 같은 알고리즘을 써야 하는 것은 아니다.
- **Reno는 TCP 혼잡제어를 배우는 대표적인 고전 모델**이며 모든 최신 TCP가 Reno로 동작한다는 뜻은 아니다.

## Ⅵ. 흐름제어와 비교

| 비교 기준 | 혼잡제어 | 흐름제어 |
|---|---|---|
| 목적 | 네트워크 과부하 방지 | 수신 측 버퍼 초과 방지 |
| 기준 자원 | 네트워크 경로·큐·용량 | 수신 측 버퍼 여유 |
| 핵심 변수 | **CWND** | **RWND** |
| 조절 주체 | 송신 측 혼잡제어 알고리즘 | 수신 측 광고·송신 측 준수 |
| 주요 신호 | 손실, RTT, ECN 등 | ACK의 Receive Window 광고 |
| 결과 | 혼잡 정도에 따라 송신량 변경 | 수신 가능한 양 이내 전송 |

## Ⅶ. 기술사 답안 작성 틀 / 시험 직전 인출

1. **정의:** 네트워크 혼잡 상태 기반 CWND 동적 조정.
2. **구성도:** 송신 TCP(CWND·ssthresh) → 네트워크 → 수신 TCP → ACK 피드백.
3. **핵심 제어:** Slow Start(지수) / Congestion Avoidance(선형) / Fast Retransmit(3 Dup ACK) / Fast Recovery(Reno).
4. **알고리즘:** Tahoe·Reno·NewReno·BIC·CUBIC·H-TCP / Vegas·FAST / Westwood(대역폭 추정).
5. **비교:** 혼잡제어 CWND vs 흐름제어 RWND.
6. **기대효과:** 혼잡 붕괴 방지, 링크 활용도·전송 안정성 향상.

**본인 인출 기록:** 지수·선형 증가, Timeout과 3 Dup ACK 차이, Reno 빠른 회복 원리를 스스로 설명함. 다만 알고리즘 전체 비교 및 도식/종합 목차는 독립 인출 재확인 필요.

# ⑥ 네트워크 오류제어(Network Error Control)

**학습 상태(2026-10-27):** 정의 19/20, ARQ 3방식 18/20, FEC/BEC 17/20, 오류 검출 기술 19/20; **전체 구성도 독립 재현 보완**.

## Ⅰ. 개요

### 1. 정의

> **네트워크 오류제어란 데이터 전송 중 발생하는 오류를 검출하고 오류 정정 또는 재전송을 통해 데이터 전송의 신뢰성을 확보하는 제어 기법이다.**

### 2. 특징

| 구분 | 특징 | 설명 |
|---|---|---|
| 신뢰성 | 전송 오류 탐지·복구 | 데이터 오류·손실에 대응 |
| 오류 검출 | 오류 발생 여부 판정 | Parity·Checksum·CRC 등 활용 |
| 오류 정정 | 수신 측 자체 정정 | FEC와 정정부호 사용 |
| 재전송 복구 | 손상·손실 데이터 재요청 | BEC 및 ARQ 사용 |
| 성능 절충 | 오버헤드와 지연 | 부호 중복량·재전송량 간 선택 |
| 환경 적응 | 링크 특성별 적용 | 오류율·지연·피드백 가능 여부에 따라 선택 |

## Ⅱ. 오류제어 전체 구성도

```text
                   [전송 중 오류·손실 발생]
                             │
           ┌─────────────────┴──────────────────┐
           ▼                                    ▼
 [FEC : 전방 오류정정]                  [BEC : 후방 오류정정]
 송신 측 중복 정정부호 삽입               수신 측 오류 검출
           │                                    │
  수신 측 정정부호로 자체 복원       ACK/재전송 요청·Timeout 처리
           │                                    │
    재전송 없이 오류 정정                    [ARQ 재전송]
           └──────────────────┬─────────────────┘
                              ▼
                      [데이터 신뢰성 확보]
```

> **주의:** Error Detection(오류 **검출**)과 Backward Error Correction(후방 오류 **정정**)은 다르다. BEC는 오류를 검출한 뒤 피드백/재전송으로 복구하는 계열이다. 이 구성도는 개념을 비교하기 위한 것으로 실제 시스템은 검출·정정·재전송을 조합하기도 한다.

## Ⅲ. 오류 검출 기법

| 구분 | 기술 | 기본 원리 | 특징·한계 |
|---|---|---|---|
| 비트 검사 | **Parity Bit** | 1의 개수를 짝수/홀수가 되도록 조정 | 단순, 짝수 개 비트 반전 등의 오류는 놓칠 수 있음 |
| 합계 검사 | **Checksum** | 데이터 워드를 합산해 검사 값 비교 | 비교적 간단, 동일 체크섬을 만드는 오류에는 한계 |
| 다항식 검사 | **CRC** | 생성다항식에 의한 GF(2) 나눗셈의 나머지 검사 | 버스트 오류 검출에 강함(성능은 다항식과 길이에 의존) |

### 계산 원리 한눈에

- **Parity = 1의 개수 세기:** `1011`은 1이 3개 → 짝수 패리티를 만들면 패리티 비트 `1` 추가.
- **Checksum = 합계 검사:** 개념적으로 합계를 비교하되, 인터넷 체크섬은 **1의 보수 덧셈 및 보수** 같은 구체적 규칙을 쓴다.
- **CRC = 나머지 검사:** 통상적인 정수 나눗셈이 아니라 **modulo-2 이진 다항식 연산**을 사용한다.

**암기:** `패리티 = 개수 / 체크섬 = 합계 / CRC = 나머지`.

## Ⅳ. FEC와 BEC

| 비교 기준 | FEC(Forward Error Correction) | BEC(Backward Error Correction) |
|---|---|---|
| 명칭 | 전방 오류정정 | 후방 오류정정 |
| 핵심 원리 | 정정부호를 통해 수신 측 자체 복구 | 오류 검출 후 송신 측 재전송으로 복구 |
| 피드백 필요성 | 해당 정정에 재전송 피드백 불필요 | 일반적으로 ACK·NACK·타이머 등 필요 |
| 주요 비용 | 정정부호 중복·복호 복잡도 | 재전송 트래픽·왕복 지연 |
| 유리한 환경 | 긴 RTT, 피드백 곤란, 방송 등 | 재전송 가능하고 RTT·오류 특성이 적합할 때 |
| 대표 기술 | Hamming, RS, BCH, 길쌈, Turbo | ARQ 계열 |

### 1. FEC의 부호화 방식

| 구분 | 기술 | 핵심 원리 |
|---|---|---|
| 블록 부호 | **Hamming Code** | 블록에 검사 비트를 더해 제한된 비트 오류 검출·정정 |
| 블록 부호 | **Reed–Solomon** | 심벌 단위 다중·버스트 오류 정정 |
| 블록 부호 | **BCH** | 설계된 정정 능력 내 다중 비트 오류 정정 |
| 길쌈 부호 | **Convolutional Code** | 현재 입력과 부호기의 이전 상태를 반영한 연속 부호화 |
| 연접 부호 | **Turbo Code** | 복수 부호기·반복 복호로 강력한 정정 성능 구현 |

**학습 중 기억 보완:** 사용자는 '블록은 받은 블록 내에서, 비블록은 이전 데이터까지 합해서 정정'이라고 설명했다. 엄밀하게는 길쌈 부호에서 **현재 입력과 이전 입력의 영향이 반영된 상태를 사용하여 부호화**하며, '이전 데이터를 그대로 더한다'는 의미는 아니다.

### 2. BEC: ARQ의 개요

- **ARQ(Automatic Repeat reQuest)**: 수신 확인과 오류·손실 판단에 따라 필요한 데이터의 재전송을 수행하는 오류 복구 방식.
- ARQ는 **재전송의 방식**이며 모든 ARQ가 OSI L2에서만 실행되는 것은 아니다.
- 교과서의 ARQ 그림은 흔히 **프레임 단위** 순서번호를 예시로 쓴다. 실제 순서번호의 해석은 적용 프로토콜의 설계에 따른다.

## Ⅴ. ARQ 세 방식 비교

| 비교 기준 | Stop-and-Wait ARQ | Go-Back-N ARQ | Selective Repeat ARQ |
|---|---|---|---|
| 기본 동작 | 1개 전송 → ACK 확인 후 다음 | 윈도우 범위에서 여러 개 연속 전송 | 윈도우 범위에서 여러 개 연속 전송 |
| ACK | 개별 전송 확인 | **누적 ACK** | 각 데이터의 선택적/개별 확인 |
| 오류 시 재전송 | 미확인 데이터 재전송 | **오류·손실된 데이터부터 이후 전송분까지** | **손실·오류 데이터만 선택 재전송** |
| 순서가 어긋난 후속 데이터 | 원칙상 동시 수신 관리 불필요 | 교과서 모델에서 **폐기** | **수신 버퍼 보관 후 재정렬** |
| 수신 윈도우 | 1 | 1 | 여러 개 |
| 구조·효율 | 단순하지만 긴 RTT에서 비효율 | 구현 중간, 오류 시 불필요한 재전송 | 복잡하고 수신 버퍼 필요, 오류가 있는 환경에서 재전송 효율 좋음 |

### 간단 동작 예시: 0,1,2,3을 전송했고 1이 손실

```text
Stop-and-Wait : 0 전송 → ACK 확인 → 1 전송(손실) → 1 재전송
Go-Back-N    : 0,1,2,3 연속 전송 → 1부터 재전송(1,2,3)
Selective Rep: 0,1,2,3 연속 전송 → 2,3 보관 → 1만 재전송 → 순서대로 인도
```

### 1. 순서번호 전체 가짓수와 윈도우 크기

- **순서번호 공간 N** = '번호표가 몇 종류인가'라는 뜻. `k`비트면 `N=2^k` 종류가 존재한다.
- 예: 2비트 → 번호 `0,1,2,3`의 **4종류**를 순환 사용; 3비트 → `0~7`의 **8종류**.
- 이것은 **전송할 데이터 총개수**를 의미하지 않는다. 번호는 소진되면 반복 사용하며, 오래된 데이터/ACK와 새로운 데이터를 혼동하지 않기 위해 윈도우 상한이 필요하다.

| 방식 | 교과서의 송신 윈도우 최대값 | 수신 윈도우 | 기억법 |
|---|---:|---:|---|
| Stop-and-Wait | **1** | 1 | 하나 |
| Go-Back-N | **N−1 = 2^k−1** | 1 | 하나 빼고 |
| Selective Repeat | **N/2 = 2^(k−1)** | 통상 송신 윈도우와 동일한 크기로 설계 | 절반 |

> SR의 `N/2`는 **송·수신 윈도우를 동일하게 설정한 대표적인 교과서 모델의 최대값**이다. 더 일반적으로는 순서번호 중복으로 인한 모호성을 방지하기 위한 송·수신 윈도우 크기 제약을 고려한다.

### 2. ARQ와 TCP의 SEQ를 혼동하지 않기

| 구분 | 순서번호 해석 |
|---|---|
| 교과서의 GBN·SR | 번호가 부여된 프레임 또는 추상 데이터 단위 |
| TCP | **세그먼트 헤더에 있는 SEQ는 해당 세그먼트의 첫 데이터 바이트 번호** |

예: TCP에서 `SEQ=101`로 데이터 100바이트를 정상 수신하면 **다음 기대 바이트는 201이므로 ACK=201**. 단순히 '세그먼트 한 개 받았으니 ACK=102'가 아니다. TCP에서는 SYN/FIN이 각각 순서번호 공간 1을 소비하지만, 일반 데이터는 바이트 수만큼 소비한다.

## Ⅵ. FEC·BEC 선정 고려사항 및 기대효과

| 구분 | 검토사항 | 적용 판단 |
|---|---|---|
| 오류 특성 | BER·버스트 오류 | 오류 빈도와 형태에 맞는 검출·정정능력 결정 |
| 지연 | RTT·실시간성 | 재전송 지연을 허용할 수 있는지 판단 |
| 네트워크 자원 | 대역폭·중복 부호 | FEC 오버헤드와 ARQ 재전송량 비교 |
| 단말 자원 | 처리 복잡도·버퍼 | 복호·선택 재전송의 연산/메모리 비용 고려 |
| 피드백 | 양방향 확인 채널 | ACK/NACK 사용 가능 여부 |
| 서비스 특성 | 방송·무선·위성·유선 | 링크·응용 특성에 맞는 조합 선택 |

**시험 직전 암기:** `검출 = 패·체·CRC / 정정 = FEC 자체 복구·BEC 재전송 / ARQ = 스톱 1·고백 다시·선택 해당만`.

**본인 인출 기록:** 정의, ARQ 동작, FEC/BEC, 오류 검출 세 기술의 원리는 인출함. BEC는 '후방 오류**정정**'으로 정확히 암기할 것. **전체 구성도 직접 재현 미확인**이므로 최종 완료 처리하지 않음.

# ⑦ Sliding Window(슬라이딩 윈도우)

**학습 상태(2026-10-27):** 정의 재인출 19/20, 동작 원리 설명 17/20, ACK 후 이동 원리 20/20, 송·수신 버퍼/윈도우·ACK·타이머 부분 인출. **구성도 독립 도식화 및 종합답안 인출 보완**.

## Ⅰ. 개요

### 1. 정의

> **Sliding Window란 송수신 윈도우를 이용하여 ACK 수신 전에도 여러 데이터를 연속 전송하고, 수신 확인에 따라 전송 가능 범위를 이동시켜 전송 효율을 향상시키는 전송 제어 기법이다.**

> **정의 구분:** Sliding Window 자체를 **TCP 전용 알고리즘**이라고 정의하면 안 된다. Go-Back-N, Selective Repeat의 연속 전송에도 활용되며 TCP의 흐름제어에도 적용된다.

### 2. 특징

| 구분 | 특징 | 의미 |
|---|---|---|
| 연속 전송 | 파이프라이닝 | ACK 전에도 윈도우 범위 내 여러 데이터 전송 가능 |
| 동적 범위 | 윈도우 이동 | ACK로 확인된 범위만큼 송신 윈도우 전진 |
| 전송 효율 | 대기 시간 감소 | Stop-and-Wait 대비 긴 RTT에서 링크 활용 개선 |
| 송수신 관리 | 송신·수신 윈도우 | 전송·수신 허용 범위 추적 |
| 순서 관리 | SEQ·ACK | 식별·수신 확인 및 순서 유지에 활용 |
| TCP 연계 | RWND·CWND | 수신 여유와 네트워크 혼잡 한도를 함께 준수 |

## Ⅱ. 구성도

```text
   ┌────────────────── 송신 측 ──────────────────┐
   │ 송신 버퍼  ·  송신 윈도우  ·  SEQ 관리       │
   │ 미확인 데이터 보관     ·    재전송 타이머     │
   └─────────────────┬──────────────────────────┘
                     │ ① 데이터 세그먼트(SEQ 포함)
                     ▼
   ┌────────────────── 수신 측 ──────────────────┐
   │ 수신 윈도우  ·  수신 버퍼  ·  순서 관리       │
   │ 연속 수신 확인 및 ACK 생성 / RWND 광고      │
   └─────────────────┬──────────────────────────┘
                     │ ② ACK + RWND 광고(TCP 적용)
                     └──────────────────────────► 송신 측
                           │
                           ▼
                 ③ 송신 윈도우 오른쪽 이동
                           │
                           ▼
                       ④ 추가 전송
```

**화살표 구별:** 송신 측→수신 측은 **데이터(그 안에 SEQ 포함)**, 수신 측→송신 측은 **ACK(및 TCP의 RWND 광고)**이다. SEQ가 독립된 별도 데이터 메시지라는 뜻이 아니다.

## Ⅲ. 구성요소 및 역할

| 구분 | 구성요소 | 역할 |
|---|---|---|
| 송신 저장 | **송신 버퍼** | 보낸 데이터를 ACK 수신 전까지 보관하여 필요시 재전송 |
| 수신 저장 | **수신 버퍼** | 도착한 데이터를 보관; 순서 재구성에 활용 가능 |
| 송신 범위 | **송신 윈도우(Sender Window)** | 미확인 상태로 전송을 허용하는 데이터 범위 |
| 수신 범위 | **수신 윈도우(Receiver Window)** | 수신 측에서 허용되는 데이터 범위 |
| 식별·확인 | **SEQ·ACK** | 송신 데이터의 위치 식별, 수신 확인 및 윈도우 이동 |
| 오류 복구 지원 | **재전송 타이머 / RTO** | ACK가 없을 때 재전송 시점 판단(ARQ와 결합 시) |

**버퍼 ≠ 윈도우:** 버퍼는 실제 **저장 공간**, 윈도우는 그중 현재 **송·수신을 허용하는 논리적 범위**.

**MSS ≠ 송신 윈도우:** MSS는 TCP **세그먼트 하나**의 최대 페이로드, 송신 윈도우는 **동시에 미확인 상태로 전송할 수 있는 전체 데이터 범위**.

## Ⅳ. 동작 절차와 Open / Close

1. **윈도우 설정:** 송신자는 송신 허용 범위를 정한다.
2. **연속 전송:** 범위 안의 데이터를 ACK를 기다리지 않고 여러 개 전송한다.
3. **수신 확인:** 수신 측은 프로토콜에 맞는 ACK를 회신한다(GBN·TCP는 누적 ACK, SR은 개별 확인 등).
4. **윈도우 이동:** 새로 확인된 데이터만큼 송신 윈도우 왼쪽 경계가 전진한다.
5. **새 전송 범위 개방(Open):** 오른쪽으로 이동해 새로 포함된 부분은 추가 전송 가능해진다.
6. **기확인 데이터 닫힘(Close):** ACK받은 데이터는 송신 윈도우의 왼쪽 밖으로 나가며 일반적으로 재전송 대상에서 제외된다.

```text
예시 A — 추상 데이터 단위 (각 칸 = 번호가 부여된 데이터 1개)

ACK 수신 전:    [ 1 ][ 2 ][ 3 ][ 4 ]   5    6
                └──── 송신 윈도우 ────┘

1,2가 확인됨:    1    2   [ 3 ][ 4 ][ 5 ][ 6 ]
                          └─ 새 송신 윈도우 ────┘

→ 도식적으로 오른쪽 2칸 이동 / 5,6을 새로 전송 가능
```

### TCP에서는 칸 수보다 **바이트 수**로 해석

```text
예시 B — TCP, 각 세그먼트에 데이터 1,000바이트

① SEQ=101    : 데이터 바이트 101~1100
② SEQ=1101   : 데이터 바이트 1101~2100
③ SEQ=2101   : 데이터 바이트 2101~3100

①, ② 정상 수신 → 수신 측 누적 ACK=2101
→ 확인된 2,000바이트만큼 송신 윈도우 왼쪽 경계 이동
```

- 처음 배울 때 그린 `①②③`은 **설명용 데이터 단위**이다. 이것을 실제 TCP SEQ 값 `1,2,3`으로 오인하면 안 된다.
- TCP는 **바이트 스트림**을 보내며 세그먼트 크기가 달라져도 SEQ/ACK는 바이트 번호를 따라 움직인다.
- 중복 ACK가 여러 번 왔다고 매번 윈도우가 앞으로 진행하는 것은 아니다. **새롭게 누적 확인된 데이터가 있어야** 왼쪽 경계가 전진한다.

## Ⅴ. Sliding Window와 ARQ의 관계

| 비교 기준 | Stop-and-Wait ARQ | Go-Back-N ARQ | Selective Repeat ARQ |
|---|---|---|---|
| 윈도우 활용 | 크기 1의 특수 사례 | 여러 데이터 연속 전송 | 여러 데이터 연속 전송 |
| ACK 전 송신 | 추가 전송 불가 | 송신 윈도우 한도 내 가능 | 송신 윈도우 한도 내 가능 |
| 확인 방식 | 한 개씩 확인 | 누적 ACK | 개별/선택 ACK |
| 순서 어긋난 수신 | 해당 없음에 가까움 | 후속 데이터 폐기(교과서 모델) | 후속 데이터 수신 버퍼 보관 |
| 오류 복구 | 해당 데이터 재전송 | 손실 데이터부터 후속분 재전송 | 손실 데이터만 재전송 |

- **ARQ**는 오류·손실 시 재전송하는 방식이다.
- **Sliding Window**는 ACK를 기다리는 동안 **어디까지 연속 전송하고 ACK 후 어느 범위가 새로 열리는지** 관리하는 메커니즘이다.
- 그래서 GBN·SR은 Sliding Window를 사용하는 대표적인 ARQ이며 Stop-and-Wait와의 효율 비교도 가능하다.
- '여러 개를 연속 전송하므로 수신 측이 항상 모든 후속 데이터를 버퍼링한다'는 주장은 틀리다. **GBN은 폐기**, **SR은 보관**하는 것이 교과서적 차이이다.

## Ⅵ. TCP의 흐름·혼잡제어와 연결

| 구분 | 기준 | 기능 |
|---|---|---|
| **RWND(Receive Window)** | 수신 측 버퍼 가용량 | 흐름제어: 수신 측이 감당할 수 있는 정도를 광고 |
| **CWND(Congestion Window)** | 송신 측 네트워크 혼잡 판단 | 혼잡제어: 경로가 감당할 수 있는 정도를 제한 |
| **TCP 송신 윈도우** | `min(CWND, RWND)` | 두 제한 모두 준수 |

### 계산 예시

- RWND=3KB, CWND=8KB → **3KB** (수신 측이 먼저 제한)
- RWND=10KB, CWND=2KB → **2KB** (네트워크 혼잡 한도가 먼저 제한)
- 이는 **전송 중 미확인 데이터가 없다는 가정**에서 새로 보낼 수 있는 최대량의 예다. 이미 미확인 데이터가 있다면 이를 제외하고 추가 송신량을 계산해야 한다.
- 수신 버퍼가 거의 꽉 차면 RWND는 줄어들고, RWND=0이면 송신자는 **일반 데이터 전송을 일시 중단**한다.

> **학습 범위 구분:** RWND의 광고·Zero Window·Window Probe·Persist Timer 등은 **TCP 흐름제어**에서 자세히 공부할 내용이다. 지금 완료한 **Sliding Window**와 연결되지만, 이를 이미 흐름제어 전체 학습 완료로 표시하지 않는다.

## Ⅶ. 기술사 시험 답안 구성

### 1교시 목차 예시

1. **정의:** ACK 전 연속 전송 및 ACK에 따른 윈도우 이동 기법.
2. **특징:** 파이프라이닝, 전송 효율, 송수신 윈도우, ACK 이동, 흐름제어 활용.
3. **구성도:** 송신 버퍼/윈도우 → 데이터(SEQ) → 수신 버퍼/윈도우 → ACK → 윈도우 이동.
4. **구성요소:** 송수신 버퍼, 송수신 윈도우, SEQ/ACK, 재전송 타이머.
5. **동작:** 윈도우 설정 → 연속 전송 → 확인응답 → 오른쪽 이동(Open/Close) → 추가 전송.
6. **관련 기술:** GBN·SR과의 관계, TCP에서 `min(CWND,RWND)`.

### 시험 직전 15초 인출

> **윈도우 설정 → 여러 개 연속 전송 → ACK 수신 → 왼쪽 확인분 Close → 오른쪽 새 범위 Open → 추가 전송.**
>
> **버퍼는 저장 공간 / 윈도우는 전송 허용 범위 / SEQ는 데이터 위치 / ACK는 다음 기대 위치(TCP).**

### 사용자의 독립 인출 기록

- **정의:** 최초에는 CWND/RWND로 전송량을 산출하는 모델로 설명(14/20), 이후 **ACK에 따른 이동·연속 전송을 포함해 19/20**.
- **관계:** GBN·SR에 활용하고 Stop-and-Wait 대비 한꺼번에 보내 효율적이라고 정확히 인출.
- **작동 원리:** ACK 수신만큼 윈도우 오른쪽 이동, 기확인 영역 Close·새 전송 영역 Open을 스스로 설명(17/20 종합 설명).
- **구성요소:** 버퍼, ACK, 수신 윈도우, 타임아웃을 스스로 떠올림. 송신 윈도우를 MSS와 혼동한 부분은 보완함.
- **구성도:** 송신 측 데이터(SEQ 포함) / 수신 측 ACK라는 두 방향을 확인했으나 **독립적인 전체 도식 재현은 미확인**.
- **오해 보완:** GBN이 수신 후속 데이터를 폐기하는 반면 SR은 보관. Sliding Window를 TCP 전용 알고리즘으로 정의하지 않기.

**학습 상태 결론:** Sliding Window의 정의·특징·동작 원리는 인출 확인됨. **구성도 독립 재현 및 기술사 종합 답안은 보완**, 다음 토픽은 **TCP 흐름제어(Zero Window·Window Probe 등)**.

# ⑧ Open RAN — 제132회 정보처리기술사 기출 통합 정리 (2026-10-29)

> **자료 기준:** 사용자가 제공한 132회 기출 해설 이미지 3쪽. 문제 요구: **가. Open RAN의 개념 / 나. Open RAN의 구성요소 / 다. RAN과 Open RAN의 비교**. 아래에서 **[교재]**는 해설에 제시된 범위, **[이해 보충]**은 학습을 위해 설명한 내용이다.

## Ⅰ. 사람말 원리 — 무엇을 왜 개방하는가?

- **RAN(Radio Access Network, 무선접속망):** 스마트폰·AGV 등 단말을 이동통신 코어망에 무선으로 접속시키는 망. 5G 특화망 전체와 동의어가 아니고, 특화망의 무선접속 구간이 RAN이다.
- **기지국 기능을 구성하는 유닛(Unit):** RU(Radio Unit)는 전파를 송수신하고, DU(Distributed Unit)는 빠른 무선 데이터 처리·자원 배분을 담당하며, CU(Centralized Unit)는 무선 연결 제어 및 상위 무선 프로토콜 처리를 담당한다. 각각 실제 장비·서버·소프트웨어 형태로 구현할 수 있고 반드시 물리적으로 3대로 분리되는 것은 아니다.
- **기존 RAN도 RU·DU·CU를 둘 수 있다.** Open RAN은 이를 처음 발명한 기술이 아니다. 기존의 제조사 종속적 연결을 개방형 인터페이스로 바꾸어 **다중 벤더 상호운용성**을 확보하려는 접근이다.
- **[교재] 도입 배경:** 벤더 종속성 탈피, 네트워크 구축 효율성 향상, 개방형 아키텍처 확산.
- **[이해 보충] RU와 O-RU:** 둘 다 무선 신호를 다루지만, O-RU는 O-RAN Open Fronthaul 등 필요한 개방형 규격을 지원하도록 구현된 RU를 가리킨다. 아무 RU나 다른 회사 DU에 꽂는다고 작동하지 않으며 상호운용성 검증도 필요하다. O-DU/O-CU도 해당 개방형 연동 구조에 적합해야 한다.
- **Traditional RAN:** '기존/전통적 방식'이라는 뜻이지 명칭 자체가 보급률 통계는 아니다. **Open RAN = 오픈소스 필수**도 아니다.

## Ⅱ. 정의·특징

**[기술사 정의]** Open RAN(Open Radio Access Network)이란 **무선접속망의 기능을 분리하고 개방형 인터페이스를 적용하여 다중 벤더 간 상호운용성과 네트워크 구축·운영 유연성을 확보하는 개방형 무선접속망 아키텍처**이다.

| 구분 | 특징 | 설명 |
|---|---|---|
| 개방성 | 개방형 인터페이스 | 제조사 전용 인터페이스 종속 완화 |
| 상호운용성 | 다중 벤더 | 서로 다른 제조사의 유닛 조합 가능(연동 시험 필요) |
| 모듈성 | 기능 분리 | RU·DU·CU 역할 구분 및 개별 구현·배치 가능 |
| 유연성 | 범용 HW·SW 활용 | 가상화·범용 인프라 활용 가능(필수 조건은 아님) |
| 지능화 | RIC 기반 최적화 | 정책·데이터 분석에 따른 무선망 성능 개선 지원 |
| 효율화 | 벤더 선택권 | 구축·확장 선택지 증가(통합 복잡도 고려) |

## Ⅲ. 전체 구성도 — 데이터 경로와 제어 경로 구분

```text
  [운영·지능형 최적화 — 별도 제어 경로]
  SMO / Non-RT RIC (장기 정책·운영 관리)
              | A1 (정책 연계)
       Near-RT RIC (준실시간 무선망 최적화)
              | E2 (RAN 노드와 제어·상태 연계)
              +----------------> O-CU / O-DU 등

  [무선 데이터 경로]
  UE(단말·AGV)
      ↕ 무선
  O-RU (RF / Low PHY) — 무선 송수신
      ↕ Open Fronthaul
  O-DU (RLC / MAC / High PHY) — 실시간 무선 처리
      ↕ F1 (Midhaul 구간)
  O-CU (RRC / PDCP / SDAP) — 상위 무선 프로토콜·연결 제어
      ↕
  5G 코어망 → 기업망·인터넷 [전체 이동통신 구조 이해용, 이번 교재 핵심 구성요소 표에는 없음]
```

**주의:** RIC는 사용자 패킷이 RU→DU→CU처럼 직렬로 통과하는 장비가 아니다. 무선망 최적화·제어 기능을 나타내는 별도 경로이다.

## Ⅳ. 구성요소 및 '기반기술' — [교재 2쪽 구성요소 표 기준]

| 구분 | 구성요소 | 기반기술(교재 용어) | 사람말 기능 / 기술사 서술 |
|---|---|---|---|
| 지능형 제어 | **RIC** (RAN Intelligent Controller) | Near-RT RIC / Non-RT RIC | 데이터 수집·분석으로 RAN 요소·자원 제어 및 최적화. Near-RT는 준실시간 조정, Non-RT는 장기 정책·분석 중심 |
| 중앙집중 처리 | **O-CU** (O-RAN Centralized Unit) | RRC, SDAP, PDCP | 무선 연결 제어 및 상위 데이터 처리; CU Control Plane / CU User Plane으로 구분 가능 |
| 분산·실시간 처리 | **O-DU** (O-RAN Distributed Unit) | RLC, MAC, High PHY | 무선 자원 스케줄링, 데이터 처리·재전송 등 시간에 민감한 무선 작업 수행 |
| 무선 송수신 | **O-RU** (O-RAN Radio Unit) | DFE, RF FE, Low PHY, Beamforming | 안테나와 연계하여 디지털/무선 신호 변환·송수신 및 빔 처리 |

### 기반기술의 뜻 — 깊은 알고리즘보다 장치와 기능 연결 우선

| 소속 | 약어 | 사람이 이해할 기능 |
|---|---|---|
| RIC | Near-RT RIC / Non-RT RIC | 준실시간 무선망 최적화 / 장기 정책·분석 |
| O-CU | RRC | 무선 연결 설정·변경·해제 등 제어 |
| O-CU | SDAP | 5G QoS 흐름과 무선 베어러 매핑 |
| O-CU | PDCP | 무선 데이터 전달 처리·보안 등 |
| O-DU | RLC | 데이터 분할·재조립, 일부 재전송 처리 |
| O-DU | MAC | 무선 자원 스케줄링·HARQ 등 |
| O-DU | High PHY | 물리계층 중 상위 처리 |
| O-RU | DFE | 디지털 프런트엔드 신호 처리 |
| O-RU | RF FE | 무선 고주파 신호 송수신 회로 처리 |
| O-RU | Low PHY | 물리계층 중 하위 처리 |
| O-RU | Beamforming | 특정 방향으로 송수신 신호를 집중하는 기술 |

**암기 수준:** ① 네 구성요소의 명칭과 역할 **우선 필수** → ② CU=RRC·SDAP·PDCP, DU=RLC·MAC·High PHY, RU=DFE·RF FE·Low PHY·Beamforming, RIC=Near-RT·Non-RT의 **소속 연결** → ③ 각각의 깊은 내부 알고리즘은 이번 문제의 필수 학습 범위를 벗어남.

### 개방형 연동 기반기술 — [교재 구성도 + 이해 보충]

| 연결 구간 | 명칭 | 의미 | 학습 우선순위 |
|---|---|---|---|
| O-RU ↔ O-DU | **Open Fronthaul** | 무선 신호 관련 데이터의 개방형 연동 | 핵심 |
| O-DU ↔ O-CU | **F1**, Midhaul 구간 | 분산/중앙 처리 유닛 간 연결 | 핵심 |
| Near-RT RIC ↔ RAN 노드 | **E2** | RAN 상태 수집·제어 연계 | 교재 그림 이해용 |
| Non-RT RIC ↔ Near-RT RIC | **A1** | 정책·정보 전달 | 교재 그림 이해용 |

**교재와 보충의 경계:** A1·E2는 교재의 **구성도에 표시**되지만 구성요소 설명표에서 독립 서술 항목으로 깊이 설명하지 않는다. 5G 코어망과의 연결 인터페이스 상세는 이 문제의 핵심 암기 범위에서 제외한다. **eCPRI라는 이름 자체가 완전한 Open RAN 연동을 보장하지 않으며**, 규격 준수·호환성 검증이 필요하다.

## Ⅴ. 기존 RAN(Traditional RAN)과 Open RAN 비교 — [교재 3쪽]

| 구분 | 기존 폐쇄형 RAN | O-RAN(Open RAN) |
|---|---|---|
| 장비 존재 | RU·DU·CU 구성 가능 | O-RU·O-DU·O-CU 기능 구성 |
| 공급 | 단일 벤더 중심 | 다중 벤더 연동 지향 |
| 플랫폼 | 벤더 전용 HW·SW 및 통합 구현 중심 | 범용 HW·가상화 기반 구현 활용 가능 |
| 인터페이스 | 제조사 전용·폐쇄형 연동 가능 | 개방형 인터페이스 적용 |
| 모듈성 | 벤더별 구성·연동 제약 | 기능별 독립 구현·선택 및 연동 지향 |
| 애플리케이션·운영 | 제조사 중심 관리·제어 기능 | RIC·SMO 등 프로그래밍·지능형 운영 지원 |
| 기대효과 | 검증된 통합·운영 방식 | 벤더 선택권, 상호운용성, 유연성 확대 |

**그림 읽기:** 왼쪽 `CPRI or eCPRI(closed)`, `Mid-haul(closed)`, `proprietary interfaces/software`, `single vendor`와 오른쪽 `eCPRI(open)`, `Mid-haul(open)`, `open interfaces`, `multi vendor`의 **차이는 장비의 존재가 아닌 연결의 개방성**. 교재 표기는 대비를 위한 단순화이며 기존 RAN도 가상화/기능 분리가 가능하고, Open RAN도 독점 SW를 사용할 수 있다.

## Ⅵ. 기술사 답안 골격과 학습 상태

**출제 요구별 작성 틀**
